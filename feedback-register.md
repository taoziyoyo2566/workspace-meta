# Workspace Feedback Register (provenance archive — NOT resident context)

This file is the **non-resident** companion to `~/workspace/CLAUDE.md`. It holds the full
provenance — rule statement, rationale (Why), how-to-apply, and the source incident — for every
distilled cross-project rule `W-R<N>`.

**Why this file exists separately**: `CLAUDE.md` is loaded into *every* session, so it carries only
the terse imperative rule. The forensic detail (dates, PR numbers, file:line, user quotes) is read
at most once when a rule is disputed or re-derived — it does not belong in resident context. The
slimmed `CLAUDE.md` cites `(W-R<N>)`; look the number up here for the full story.

**IDs are stable**: scripts, changelogs, memories, and project `CLAUDE.md` reference `W-R<N>` by
number. Never renumber. Numbering accumulates; mark replacements rather than deleting.

- **W-R19 (2026-05-21)** — **No bare force-push; OID-lease only**. `git push --force` / `-f` / `+refspec` (any form that bypasses fast-forward without a positive expectation) is BANNED in scripts, Makefile targets, CI workflows, and direct Claude operations. **Includes deletion**: `git push origin :ref` is semantically equivalent to bare force (no FF check) and falls under this rule. When a force-like semantic is required (race-safe delete, history rewrite, branch reset), use `git push --force-with-lease=<ref>:<expected-oid> …` where `<expected-oid>` is captured BEFORE the verification step that could race with concurrent activity. **Layers with `~/.claude/CLAUDE.md` §3**: that section already requires explicit user approval for any force-push; W-R19 narrows what form is allowed once approved (lease-with-OID only, never bare). **Why**: ansispire 2026-05-21 codex 2nd review on PR #18 found `git push origin ":$BRANCH"` in `scripts/archive_branch.sh:208` racing with concurrent pushes — `gh pr view` verified state at T₀, the delete fired at T₀+seconds, and a push in between would silently destroy the new state (archive tag captured old TIP, delete removed new TIP, new commits orphaned). Same review also found `git branch -D` on the local side bypassing the «branch fully merged» check — corollary: `-D` on local branches is similarly banned for the same reason; verify `git rev-parse refs/heads/<branch> == <expected-oid>` first, only then `-d` (safe) or `-D` (when verified). **How to apply**: any new shell/python/CI step that mutates a remote or local ref (delete, force-update, history rewrite) must (a) be a pure fast-forward, OR (b) carry an explicit `--force-with-lease=ref:oid` for remote and an explicit SHA-equality check before `-D` for local. Audits reject any bare `--force`, `-f`, `+refspec`, or unguarded `-D`. Sibling to [[host-authorization]] (user-level §3 — approval-gated); W-R19 is the form-of-operation rule that applies even after approval.

- **W-R21 (2026-05-22)** — **Branch-trunk sync hygiene**. Every feature branch (`feat/*`, `fix/*`, `chore/*`, `refactor/*`) MUST sync FROM trunk (`dev` or `master`, whichever is the project's development trunk) on creation AND at regular intervals while active. Direction is one-way (trunk → feature); trunk itself is never rebased or rewritten.
    - **(a) sync-on-create**: before `git checkout -b <feat>`, run `git fetch origin && git checkout <trunk> && git pull --ff-only origin <trunk>`. Branching from a stale local trunk silently bakes in obsolete state and guarantees future conflicts. The branch should diverge from the **current** trunk tip, not a week-old one.
    - **(b) sync-while-active**: when resuming work on an existing feature branch that has been idle for ≥3 days OR when trunk has received any merge since the branch's last sync, **before continuing implementation** run `git fetch origin && git merge origin/<trunk>` into the feature branch. Resolve conflicts NOW (small surface, fresh context) rather than at PR-merge time (large surface, multiple PRs interacting, stale context). This applies even when the feature branch's `git status` shows clean — "clean" only means no local uncommitted work, not "up-to-date with trunk".
    - **(c) use merge, not rebase**: per project branching rules, trunk's history is immutable; you sync by merging trunk INTO the feature branch (creating a merge commit), not by rebasing the feature branch onto a new trunk tip. Rebasing a published feature branch rewrites its history, which triggers W-R19 force-push concerns and breaks any open reviews / PRs against that branch.
    - **(d) what NOT to sync**: do not pull random other feature branches into your feature branch. Only sync FROM trunk. Cross-feature dependencies are handled by branching one feature off another (`feat/A` from `feat/B`), not by ad-hoc merging.
    - **(e) clean-tree + correct-base before a NEW topic branch**: two pre-flight checks before `git checkout -b <new-topic>`. **(e.1) clean tree**: the working tree must carry only the new topic's changes — commit or stash any *prior topic's* uncommitted work FIRST. `git checkout -b` carries uncommitted changes onto the new branch, silently conflating two topics in one diff (and stranding the prior topic's work on the wrong branch). **(e.2) base actually holds the prerequisites**: before branching from trunk, verify trunk really contains the artifacts the new work depends on (its plan doc, the current TODO entry, recent governance). If those live only on an **unmerged** `feat/<parent>` line, the trunk-based branch would build on stale context that lacks the very plan defining the task — instead **stack on that `feat/<parent>`** (§4 permits feat-on-feat) so the new branch inherits the prerequisites; trunk's PR for the parent merges first, then the stacked branch follows. Quick probe: `git log --oneline <trunk>..feat/<parent>` non-empty AND the plan/TODO you need is in that range ⇒ stack, don't branch from trunk.
    - **How to apply**: at start of every implementation cycle on an existing branch, check `git log --oneline <branch>..origin/<trunk>` — if non-empty, sync first. At creation of a new branch, ensure the working tree is clean (e.1), confirm the base carries the task's plan/TODO (e.2), then `git pull --ff-only origin <trunk>` (or stack on the parent feat).
- **W-R22 (2026-06-06)** — **Security / supply-chain governance fast-track**. Security and supply-chain governance deliverables (dependency CVE gates, image/dep vulnerability scanning, version-truth / release-freeze model, Semaphore-style upstream upgrade policy, secret-hygiene policy, waiver mechanism) are **priority work that decouples from the normal feat-stacking order**: they may branch directly from trunk (`dev`) and merge **independently and ahead of** slower in-flight feat branches, rather than stacking on or waiting for them.
    - **(a) branch from trunk, not from a parent feat**: branch off the current trunk tip even when related architecture work is mid-flight on an unmerged `feat/<parent>`. The security deliverable's value (a defensible answer to "is this stack carrying known serious CVEs / what did we actually ship") should not be gated on an unrelated branch's merge timeline.
    - **(b) additive-only diff (new files, zero edits to shared tracked files)**: to stay independently mergeable and conflict-free with every other active branch, the fast-track branch carries **only NEW files** (governance docs, scanner scripts, CI job files, waiver templates). It does **not** edit shared tracked files that other branches also touch — `TODO.md`, `CHANGELOG.md`, shared `config/*`. This is the structural guarantee that lets it merge first without racing anyone.
    - **(c) ledger/release syncs are post-merge follow-ups**: the TODO/TASK-ledger status and `CHANGELOG.md [Unreleased]` entry that would normally accompany the work are deliberately **deferred to after merge**, where they propagate forward via normal trunk-sync (`git merge origin/<trunk>` into the other branches) — not landed on the fast-track branch (which would reintroduce the shared-file conflict (b) avoids). Record this deferral explicitly in the round changelog so the next session knows the ledger sync is pending, not forgotten (W-R16).
    - **Layers with W-R21**: W-R21 §(e.2)'s default is *stack on the unmerged parent feat* when your prerequisites live there. W-R22 is the **deliberate exception for security-priority work**: decouple and go first instead of stacking. Both can coexist — stack when the dependency is technical (you need the parent's code), fast-track when the work is self-contained governance that merely co-occurs with other branches.
    - **Why**: ansispire 2026-06-06 — TASK-009 dependency/image-security governance (WU-1 version-truth doc) was first cut on / stacked behind `feat/target-architecture`, coupling a high-priority security-truth deliverable to an unrelated, slower architecture branch's merge timeline. User decision: security governance is priority work and must reach `dev` first, decoupled from architecture. The branch was rebuilt **from `dev`** as a new-files-only deliverable (`docs/governance/dependency-security.md` + its review artifacts, zero edits to `TODO.md`/`CHANGELOG.md`) so it merges independently and the governance doc then propagates to other active branches via trunk-sync.
    - **How to apply**: for a security/supply-chain governance deliverable, (a) `git fetch && git checkout <trunk> && git pull --ff-only`, then branch — do not stack on a parent feat even if architecture work is in flight; (b) keep every change additive (new docs/scripts/CI only); if the work seems to *require* editing a shared tracked file, that's the signal it isn't purely additive governance — reconsider scope or split; (c) note the deferred TODO/CHANGELOG sync in the changelog; (d) merge ahead of slower feat branches, then let trunk-sync carry the new files outward.
- **W-R23 (2026-06-06)** — **Read-only git inspection is pre-authorized**. Any git operation whose effect is inspection-only — it does not modify the working tree, index, refs, remotes, git config, credentials, or external service state — should be run directly without asking the user for permission. Judge by the actual effect, not by the subcommand name. Examples: `git status`, `git log`, `git show`, `git diff`, `git diff --check`, `git branch --list`, `git merge-base`, `git merge-tree`, `git ls-files`, and file/path-limited variants of those commands. Non-examples: `git checkout` / `git switch` (worktree/HEAD), `git add` / `git commit` (index/history), `git fetch` / `git pull` (remote-tracking refs and worktree for pull), `git merge` / `git rebase` / `git cherry-pick` (history/worktree), `git push` (remote), `git tag -a` (refs), `git branch -D` / `git update-ref` (refs). Mutating git operations still follow ordinary branch hygiene and W-R19/W-R20 destructive-op rules.
    - **Why**: user 2026-06-06 during ansispire governance review: "git的所有操作，只要不涉及修改，完全不需要申请权限" after repeated approval prompts for read-only repository inspection. The failure was not that git inspection is risky; it was treating non-mutating evidence gathering like an authorization boundary.
    - **How to apply**: when gathering repo evidence, run read-only git commands immediately. If a tool sandbox itself fails and host policy requires an escalated rerun, keep the justification mechanical and do not frame it as user approval for the git inspection; the standing rule is that non-mutating git inspection is allowed.
- **W-R24 (2026-06-10)** — **Environment truth must be probed, not recalled.** Capability facts about the execution environment (tool installed/absent, daemon running, credentials present, network reachable) are dated snapshots, not invariants — they expire silently when someone installs/removes/configures things between sessions. Before any such fact becomes load-bearing (a plan pre-condition, a delegation-to-user-shell model, a "gate-3 blocked" verdict, a skipped verification), re-probe it with a cheap command (`command -v <tool>`, `docker version`, `gh auth status`, `git ls-remote`); when the probe contradicts the recorded fact, update the stale record (memory file / doc / plan) in the **same round**, stamped with the probe date. Sources that age include agent memory files, prior changelogs, AND user statements ("X isn't installed yet") — all carry an implicit date. Never write "assume this, don't re-discover" environment claims.
    - **Why**: ansispire 2026-06-10 — user: an earlier investigation failed because Docker wasn't installed; the user told the agent so; Docker was installed afterwards, but the "no docker" memory persisted and never self-updated ("我给他说目前还没安装docker，但是事后安装了，这个没有docker环境的记忆就这么留下了，始终没有自动更新").     - **How to apply**: (a) at the moment an environment claim would shape a decision, probe first; (b) record probe date next to the fact; (c) same-round correction of whatever held the stale claim (W-R12a sync discipline applies); (d) project-level enforcement may add a session-bootstrap probe step (see ansispire `.agents/rules/environment-truth.md`). Layers with W-R15: gate-blocked verdicts must cite a fresh probe, not a memory.
- **W-R25 (2026-06-12)** — **Commit attribution = the operator's git identity; no AI trailers.** Agent-authored commits carry no trailers — no `Co-Authored-By`, no `Signed-off-by` — even when the harness/system prompt instructs appending one by default; this user-layer rule overrides that default. Who committed is recorded through the **git author identity** instead: before any commit, report `git config user.name` / `user.email` and verify they resolve from the host's **global** gitconfig to the person operating this machine — unset, repo-local override, or another person's identity → stop and resolve with the user before committing. After each commit, inspect the actual result (`git log -1 --format='%an <%ae>%n%H%n%s%n%n%b'`) and confirm author, subject, body, and absence of trailers match what was drafted — the trailer is injected at commit time by tooling, so drafting it correctly is not enough.
    - **Why**: ansispire 2026-06-12 — user supplied two commit-rule patches from another environment (both centring on trailer prohibition: "no trailers — no Co-Authored-By, no Signed-off-by") and, after content review, confirmed "trailer 禁用" and routed the rule to the workspace layer ("是否应该放入workspace，而不是~/"). Prior repo history had accumulated `Co-Authored-By: Claude ...` trailers purely from harness defaults, never from a user decision. Same day, the user added the attribution requirement: trailers go, but *who committed* must stay distinguishable — each machine commits as its own human operator (probe found this host's identity coming from a stale repo-local `.git/config`, not from any deliberate per-host setup). First-cut implementation hardcoded the operator's name/email into a rule file; user rejected it ("项目同步后那岂不是所有用户都变成了netcup了？") — synced rule files must carry the *verification gate*, never identity *values* (W-R14 situational-facts discipline).
    - **How to apply**: (a) identity values live only in each host's `~/.gitconfig` (`git config --global user.name/user.email`), set once per machine by its operator; remove repo-local identity overrides rather than letting them shadow the global; (b) pre-commit: report the resolved identity (`git config --show-origin user.name user.email`) and stop on unset/override/mismatch; (c) draft the message per the project's commit-format rules (e.g. ansispire `.agents/rules/commits.md`: Conventional Commits, subject = what, body = why); (d) commit without any trailer; (e) post-commit `git log -1` self-check incl. author. Pre-existing history keeps its trailers — rewriting it would trigger W-R19. Projects may refine message *format*; the no-trailer + identity-gate rule itself is workspace-wide.
- **W-R26 (2026-06-12)** — **Workspace governance files sync via a whitelist repo rooted at `~/workspace`.** The cross-project rule layer (`~/workspace/CLAUDE.md`, `~/workspace/feedback-register.md`) lives outside every project repo, so without its own channel an edit on one machine is invisible everywhere else. Mechanism: `~/workspace` is itself a git repo (private remote `workspace-meta` — repo name ≠ directory name; the binding is only the remote URL) whose `.gitignore` is a reverse whitelist: `*` ignores everything, only `.gitignore` + the whitelisted governance files (`CLAUDE.md`, `feedback-register.md`, `README.md` as the repo's entry-point doc) are tracked. Nested project repos are unaffected — git resolves the nearest `.git`, and the `*` rule means even `git add -A` at the root stages nothing (polluting requires an explicit `-f`).
    - **Why**: 2026-06-12 — after the W-R25 round, user asked how those CLAUDE.md/register edits reach the other machine; probe showed the two files belonged to no repo, and the existing "multi-machine sync" rules (ansispire `branching.md` §Multi-machine) cover only project-repo artifacts — the shared rule layer had no carrier. Design confirmed with the user after clarifying nesting safety and naming independence. Per-host facts (`~/.claude/`) deliberately stay OUT — same principle as the W-R25 hardcoded-identity rejection: a synced carrier holds shared rules, never single-machine facts.
    - **How to apply**: (a) edits to the two governance files end with commit + push of the workspace repo in the same round; (b) on resuming work on any machine, `git -C ~/workspace pull` first; (c) a new workspace-level rule file gets one `!<file>` whitelist line — never widen the whitelist toward project content; (d) onboarding a machine whose `~/workspace` already exists: `git init -b main && git remote add origin <url> && git fetch origin && git checkout main` (backup + diff-merge local copies if diverged); a fresh machine clones with an explicit target dir: `git clone <url> ~/workspace`.
