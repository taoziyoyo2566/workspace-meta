- **W-R19 (2026-05-21)** — **No bare force-push; OID-lease only**. `git push --force` / `-f` / `+refspec` (any form that bypasses fast-forward without a positive expectation) is BANNED in scripts, Makefile targets, CI workflows, and direct Claude operations. **Includes deletion**: `git push origin :ref` is semantically equivalent to bare force (no FF check) and falls under this rule. When a force-like semantic is required (race-safe delete, history rewrite, branch reset), use `git push --force-with-lease=<ref>:<expected-oid> …` where `<expected-oid>` is captured BEFORE the verification step that could race with concurrent activity. **Layers with `~/.claude/CLAUDE.md` §3**: that section already requires explicit user approval for any force-push; W-R19 narrows what form is allowed once approved (lease-with-OID only, never bare). **Why**: ansispire 2026-05-21 codex 2nd review on PR #18 found `git push origin ":$BRANCH"` in `scripts/archive_branch.sh:208` racing with concurrent pushes — `gh pr view` verified state at T₀, the delete fired at T₀+seconds, and a push in between would silently destroy the new state (archive tag captured old TIP, delete removed new TIP, new commits orphaned). Same review also found `git branch -D` on the local side bypassing the «branch fully merged» check — corollary: `-D` on local branches is similarly banned for the same reason; verify `git rev-parse refs/heads/<branch> == <expected-oid>` first, only then `-d` (safe) or `-D` (when verified). **How to apply**: any new shell/python/CI step that mutates a remote or local ref (delete, force-update, history rewrite) must (a) be a pure fast-forward, OR (b) carry an explicit `--force-with-lease=ref:oid` for remote and an explicit SHA-equality check before `-D` for local. Audits reject any bare `--force`, `-f`, `+refspec`, or unguarded `-D`. Sibling to [[host-authorization]] (user-level §3 — approval-gated); W-R19 is the form-of-operation rule that applies even after approval.

- **W-R21 (2026-05-22)** — **Branch-trunk sync hygiene**. Every feature branch (`feat/*`, `fix/*`, `chore/*`, `refactor/*`) MUST sync FROM trunk (`dev` or `master`, whichever is the project's development trunk) on creation AND at regular intervals while active. Direction is one-way (trunk → feature); trunk itself is never rebased or rewritten.
    - **(a) sync-on-create**: before `git checkout -b <feat>`, run `git fetch origin && git checkout <trunk> && git pull --ff-only origin <trunk>`. Branching from a stale local trunk silently bakes in obsolete state and guarantees future conflicts. The branch should diverge from the **current** trunk tip, not a week-old one.
    - **(b) sync-while-active**: when resuming work on an existing feature branch that has been idle for ≥3 days OR when trunk has received any merge since the branch's last sync, **before continuing implementation** run `git fetch origin && git merge origin/<trunk>` into the feature branch. Resolve conflicts NOW (small surface, fresh context) rather than at PR-merge time (large surface, multiple PRs interacting, stale context). This applies even when the feature branch's `git status` shows clean — "clean" only means no local uncommitted work, not "up-to-date with trunk".
    - **(c) use merge, not rebase**: per project branching rules, trunk's history is immutable; you sync by merging trunk INTO the feature branch (creating a merge commit), not by rebasing the feature branch onto a new trunk tip. Rebasing a published feature branch rewrites its history, which triggers W-R19 force-push concerns and breaks any open reviews / PRs against that branch.
    - **(d) what NOT to sync**: do not pull random other feature branches into your feature branch. Only sync FROM trunk. Cross-feature dependencies are handled by branching one feature off another (`feat/A` from `feat/B`), not by ad-hoc merging.
    - **(e) clean-tree + correct-base before a NEW topic branch**: two pre-flight checks before `git checkout -b <new-topic>`. **(e.1) clean tree**: the working tree must carry only the new topic's changes — commit or stash any *prior topic's* uncommitted work FIRST. `git checkout -b` carries uncommitted changes onto the new branch, silently conflating two topics in one diff (and stranding the prior topic's work on the wrong branch). **(e.2) base actually holds the prerequisites**: before branching from trunk, verify trunk really contains the artifacts the new work depends on (its plan doc, the current TODO entry, recent governance). If those live only on an **unmerged** `feat/<parent>` line, the trunk-based branch would build on stale context that lacks the very plan defining the task — instead **stack on that `feat/<parent>`** (§4 permits feat-on-feat) so the new branch inherits the prerequisites; trunk's PR for the parent merges first, then the stacked branch follows. Quick probe: `git log --oneline <trunk>..feat/<parent>` non-empty AND the plan/TODO you need is in that range ⇒ stack, don't branch from trunk.
    - **How to apply**: at start of every implementation cycle on an existing branch, check `git log --oneline <branch>..origin/<trunk>` — if non-empty, sync first. At creation of a new branch, ensure the working tree is clean (e.1), confirm the base carries the task's plan/TODO (e.2), then `git pull --ff-only origin <trunk>` (or stack on the parent feat).
- **W-R22 (2026-06-06)** — **Security / supply-chain governance fast-track**. Security and supply-chain governance deliverables (dependency CVE gates, image/dep vulnerability scanning, version-truth / release-freeze model, Semaphore-style upstream upgrade policy, secret-hygiene policy, waiver mechanism) are **priority work that decouples from the normal feat-stacking order**: they may branch directly from trunk (`dev`) and merge **independently and ahead of** slower in-flight feat branches, rather than stacking on or waiting for them.
    - **(a) branch from trunk, not from a parent feat**: branch off the current trunk tip even when related architecture work is mid-flight on an unmerged `feat/<parent>`. The security deliverable's value (a defensible answer to "is this stack carrying known serious CVEs / what did we actually ship") should not be gated on an unrelated branch's merge timeline.
    - **(b) additive-only diff (new files, zero edits to shared tracked files)**: to stay independently mergeable and conflict-free with every other active branch, the fast-track branch carries **only NEW files** (governance docs, scanner scripts, CI job files, waiver templates). It does **not** edit shared tracked files that other branches also touch — `TODO.md`, `CHANGELOG.md`, shared `config/*`. This is the structural guarantee that lets it merge first without racing anyone.
    - **(c) ledger/release syncs are post-merge follow-ups**: the TODO/TASK-ledger status and `CHANGELOG.md [Unreleased]` entry that would normally accompany the work are deliberately **deferred to after merge**, where they propagate forward via normal trunk-sync (`git merge origin/<trunk>` into the other branches) — not landed on the fast-track branch (which would reintroduce the shared-file conflict (b) avoids). Record this deferral explicitly in the round changelog so the next session knows the ledger sync is pending, not forgotten (W-R16).
    - **Layers with W-R21**: W-R21 §(e.2)'s default is *stack on the unmerged parent feat* when your prerequisites live there. W-R22 is the **deliberate exception for security-priority work**: decouple and go first instead of stacking. Both can coexist — stack when the dependency is technical (you need the parent's code), fast-track when the work is self-contained governance that merely co-occurs with other branches.
    - **Why**: ansispire 2026-06-06 — TASK-009 dependency/image-security governance (WU-1 version-truth doc) was first cut on / stacked behind `feat/target-architecture`, coupling a high-priority security-truth deliverable to an unrelated, slower architecture branch's merge timeline. - **W-R23 (2026-06-06)** — **Read-only git inspection is pre-authorized**. Any git operation whose effect is inspection-only — it does not modify the working tree, index, refs, remotes, git config, credentials, or external service state — should be run directly without asking the user for permission. Judge by the actual effect, not by the subcommand name. Examples: `git status`, `git log`, `git show`, `git diff`, `git diff --check`, `git branch --list`, `git merge-base`, `git merge-tree`, `git ls-files`, and file/path-limited variants of those commands. Non-examples: `git checkout` / `git switch` (worktree/HEAD), `git add` / `git commit` (index/history), `git fetch` / `git pull` (remote-tracking refs and worktree for pull), `git merge` / `git rebase` / `git cherry-pick` (history/worktree), `git push` (remote), `git tag -a` (refs), `git branch -D` / `git update-ref` (refs). Mutating git operations still follow ordinary branch hygiene and W-R19/W-R20 destructive-op rules.
    - **Why**: user 2026-06-06 during ansispire governance review: "git的所有操作，只要不涉及修改，完全不需要申请权限" after repeated approval prompts for read-only repository inspection. The failure was not that git inspection is risky; it was treating non-mutating evidence gathering like an authorization boundary.
    - **How to apply**: when gathering repo evidence, run read-only git commands immediately. If a tool sandbox itself fails and host policy requires an escalated rerun, keep the justification mechanical and do not frame it as user approval for the git inspection; the standing rule is that non-mutating git inspection is allowed.
- **W-R24 (2026-06-10)** — **Environment truth must be probed, not recalled.** Capability facts about the execution environment (tool installed/absent, daemon running, credentials present, network reachable) are dated snapshots, not invariants — they expire silently when someone installs/removes/configures things between sessions. Sources that age include agent memory files, prior changelogs, AND user statements ("X isn't installed yet") — all carry an implicit date. Never write "assume this, don't re-discover" environment claims.
    - **Why**: ansispire 2026-06-10 — user: an earlier investigation failed because Docker wasn't installed; the user told the agent so; Docker was installed afterwards, but the "no docker" memory persisted and never self-updated ("我给他说目前还没安装docker，但是事后安装了，这个没有docker环境的记忆就这么留下了，始终没有自动更新"). - **W-R27 (2026-06-26)** — **Match a behavior-shaping rule's form to its failure type; the register's source-incident IS the baseline test.** A rule meant to change how the agent acts under pressure only binds if its *form* fits the *failure* it targets — and prohibition, the default reflex, measurably backfires on two of the four failure types. Classify the baseline failure first, then pick the form:

    | Baseline failure | Right form | Wrong form |
    |---|---|---|
    | **Discipline-skip** — knows the rule, breaks it under pressure | Prohibition + rationalization table + red-flags + "violating the letter = violating the spirit" | Soft guidance ("prefer…", "consider…") |
    | **Wrong-shaped output** — complies, but output bloats / buries the verdict / restates the spec | Positive recipe/contract: state what the output IS — its parts, in order | Prohibition list ("don't restate", "never narrate") |
    | **Omitted element** — drops a required part of something already produced | Structural: a REQUIRED field/slot in the template they fill in | Prose reminder near the template |
    | **Condition-dependent** — behaviour should vary by situation | Conditional keyed to an observable predicate ("if the brief exists, reference it") | Unconditional rule + exemption clauses |

    - **Why prohibitions backfire on shape/omission:** under a competing incentive an agent negotiates with "don't X"; in superpowers' head-to-head wording tests the prohibition arm produced *more* of the unwanted content than both the recipe arm and the no-guidance control. A recipe leaves nothing to negotiate — output matches the stated shape or it doesn't. Two corollaries: **no nuance clauses** ("don't X unless it matters" reopens the negotiation — express a real exception as its own conditional on an observable predicate); **exemption clauses don't scope** ("this limit doesn't apply to code blocks" still suppresses code blocks — restructure so the rule can't reach the exempt part).
    - **The register already runs RED→GREEN by reality.** superpowers builds skills as TDD-for-process: RED = watch an agent fail a constructed pressure-scenario *without* the skill, GREEN = write the minimal skill, REFACTOR = close new loopholes. Our feedback loop already does RED→GREEN — but RED is supplied by the **real source incident** each W-R is required to cite, not by a constructed scenario. So the heavyweight apparatus (constructed 3+-pressure scenarios; fresh-context micro-tests with a no-guidance control, 5+ reps, every flagged match read by hand, variance-as-metric) is an **optional escalation** for high-stakes or disputed rules — not a standing gate on every rule. What we were *missing* is the other two phases made explicit: (1) **form-matching at write time** (the table above), and (2) a **REFACTOR signal** — when a landed rule *recurs in a later real session*, that recurrence is the new-rationalization evidence, and the fix is usually a **form change** (prohibition → recipe/structural), not louder language.
    - **Persuasion-principle mapping** (Meincke et al. 2025, N≈28k: persuasion framing lifted LLM compliance 33%→72%; Cialdini 2021). Pick principles by rule type: *discipline* → Authority ("YOU MUST", "No exceptions") + Commitment (announce / forced A-B-C choice / todo tracking) + Social-proof ("X without Y = failure, every time"); *collaborative/judgement* → Unity ("we're colleagues, I need your honest judgement") + moderate Authority; *reference* → clarity only, no persuasion. **Never use Liking** for compliance (breeds sycophancy — aligns with our stack's preference for honest technical pushback over performative agreement) and avoid Reciprocity (feels manipulative, rarely needed). Ethics test: would the technique still serve the operator if they fully understood it?
