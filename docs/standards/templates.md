# 简短模板

只复制本次需要的部分，删掉不适用项。文件位置、状态字段和命令沿用项目约定；示例中的任务创建接口不代表任何项目的真实需求。

## 设计方案

```markdown
# 本次要解决的问题

当前行为与问题：
完成后会发生的变化：
本次范围与不做的内容：

## 方案

受影响的模块、接口或数据及其职责变化：
实现机制与选择理由：
必要的失败、兼容性和恢复处理：
尚需确认的事实，以及何时、怎样确认：

## 验收

- 在……条件下，执行……，应看到……；通过……检查。
```

项目要求持久化 Plan 时再补项目规定的状态等元数据。已有方案承载设计就直接使用，不另建一份同内容的“设计文档”。

## 实施清单示例

以下是跨多个会话接续工作的清单示例；普通小任务可以更短。

- [ ] **确认现有任务创建行为**：定位创建入口和数据表，在测试环境复现重复提交；记录当前返回值和任务条数，作为后续验证基线。
- [ ] **增加请求键约束**：前提是明确请求键按用户隔离，并检查存量数据处理方式；修改模型与迁移。验收：测试数据库拒绝同一用户的重复键，不误伤其他用户。
- [ ] **处理重试和冲突**：依赖数据约束；修改创建入口。验收：同键同内容返回原任务，同键异内容返回冲突，并发时不重复创建。
- [ ] **验证兼容性**：在设计要求的旧数据、旧调用方和目标版本条件下执行集成测试；未通过时停止发布，回到相关步骤修复。

真实的项目清单应把入口、模型、迁移和测试替换为已确认的模块或路径。发布步骤引用该项目的部署手册，写明目标、版本、生效检查和恢复条件；通用示例不提供虚构的部署命令。

## 一次操作的记录

仅在用户需要或审计、恢复、交接确有需要时使用；记录保存在项目约定的位置。

```markdown
时间与执行者：
目标环境、范围与代码/制品版本：
对应任务或操作手册：
前置条件检查结果：
关键操作（引用手册步骤；实际有偏离时说明）：
结果与证据位置：
遗留问题、恢复状态或下一步：
```

记录不包含密码、令牌或完整敏感配置，也不复制全部终端输出。一次没有执行的操作应写“未执行”，保留未满足的条件。

## 交付或评审说明

```markdown
解决了什么问题，行为如何变化：
关键实现与影响范围：
已执行的验证及结果：
未验证项、已知限制与后续处理：
实际交付状态（例如本地修改、已合并、已部署）：
```

## 长期架构决策

仅在需要独立检索时建立 ADR；普通选择在方案中解释即可。

```markdown
# 决策标题

状态：按项目约定填写
背景：需要解决的问题与约束
决定：采用的做法和理由
影响：获得的好处、承担的代价、成立条件
关联：已有方案、后续替代决定
```

模板使用边界见[实施与交付规范](delivery.md)，文档生命周期见 [documentation.md](../../.agents/rules/documentation.md)。
