# 开发与评审规范

开发交付的是可理解、可验证、可维护的行为变化。主要规则由 [implementation.md](../../.agents/rules/implementation.md)、[verification.md](../../.agents/rules/verification.md) 和 [review.md](../../.agents/rules/review.md) 管理。

## 开始修改之前

读当前实现、相关接口和已有测试，确认工作树中哪些修改属于本次任务。找到行为和数据的唯一维护位置，沿用项目的语言、目录、格式化和框架习惯。项目应给出实际检查命令；通用规范不统一各语言的格式工具。

先确认能复现的问题或预期的新行为，再决定改哪些文件。跨模块或风险较高的改动按[设计规范](design.md)补足依据。

## 组织代码与变更

- 一次变更围绕一个完整目的，包含直接相关的测试和契约说明；无关清理另行处理。没有统一的行数或文件数上限。
- 模块职责清楚，接口表达输入、输出和失败方式。重复的业务逻辑和策略有共同维护位置；不同使用者通过参数或明确接口复用。
- 抽象应消除真实重复或分离明确职责。只有一个调用方的简单流程，不必预先做成通用框架。
- 可调整设定作为数据管理，代码负责解释、校验和执行。配置结构、默认行为、生效方式与兼容性属于接口的一部分。
- 错误不能被静默吞掉。返回或记录足以定位问题的上下文；敏感内容按项目约定处理。是否重试、如何避免重复副作用，要结合实际操作语义决定。
- 注释解释不明显的原因、约束和兼容性要求。代码已经表达的动作不再逐句复述，评审过程和修改历史由相应记录承载。

## 依赖、接口和数据变化

新增或升级依赖时，核查来源、维护状态、适用于当前用法的已知漏洞，以及生态已有的完整性校验。保留实际解析版本，例如锁文件或构建记录；复用工具输出，不手工维护第二份组件清单。许可或分发条件影响项目使用时，一并说明。

接口和数据结构变化应检查旧调用方、已有数据及混合版本运行条件。破坏性变化需要明确迁移方式和调用方处理；数据库回退要验证数据兼容性，不能只写“回到旧版本”。配置变更同样应覆盖旧值、缺失值和无效值的处理。

## 按风险选择测试

| 改动 | 通常优先的验证 |
|---|---|
| 文案、格式、导航 | 格式、链接、渲染或引用检查 |
| 算法、校验、状态转换 | 单元测试，覆盖正常与相关边界行为 |
| 数据库、协议、外部依赖 | 集成或契约测试；明确模拟环境的局限 |
| 用户关键流程 | 少量有代表性的端到端检查 |
| 实质行为缺陷 | 能识别原缺陷的回归用例；安全可行时验证修复前失败、修复后通过 |
| 认证、授权、资源归属 | 允许和拒绝路径，相关的未登录、跨用户、跨租户或低权限访问 |
| 迁移、恢复、部署 | 相应版本与数据条件下的演练及结果检查 |

测试断言用户或调用方依赖的行为，不锁死内部变量名、步骤标题等偶然写法。权限拒绝测试同时检查没有受保护数据泄露或未授权的业务状态变更；审计、限流、失败计数等预期防护副作用按项目契约验证。并非每项改动都要具备表中全部测试，也不为低影响文案新增行为测试。

静态检查只能证明它检查的范围。模拟服务通过不等于真实服务联通，健康接口正常不等于关键用户流程成功。执行必要检查后，记录范围、结果和未覆盖项；失败应定位原因，修复后重跑相关检查，不机械重复全套。

## 评审如何给出结论

先看问题是否解决、行为是否正确，再看安全、兼容性、数据风险和长期维护成本。检查测试能否发现它声称覆盖的错误。评审意见说明具体触发条件、影响和证据；审美或个人习惯应标成建议，不充当阻塞理由。

小团队可以使用同行评审、AI 辅助评审或自审，但要如实说明实际参与者与局限。多个 AI 得出相同意见仍需要代码和行为证据，不替代测试或权限审批。

交付描述先写问题与结果，再给必要的实现说明、验证和遗留限制。不得用“已完成”混指代码写好、测试通过、合并、部署和上线效果。
