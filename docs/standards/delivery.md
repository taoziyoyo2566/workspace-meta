# 实施与交付规范

实施方案把已确定的设计拆成能执行、能检查、能接续的工作。具体任务保存在项目仓库。阶段与验收由 [planning.md](../../.agents/rules/planning.md) 管理，记录归属由 [documentation.md](../../.agents/rules/documentation.md) 管理，检查结论由 [verification.md](../../.agents/rules/verification.md) 管理。改动走的分支流程由 [git-branches.md](../../.agents/rules/git-branches.md) 管理，什么可以对用户提供服务由 [deployment.md](../../.agents/rules/deployment.md) 管理，版本号、发布标签和回退目标由 [releases.md](../../.agents/rules/releases.md) 管理。

## 把任务写到可以动手

任务标题点明动作和对象，例如“为任务表增加请求键唯一约束”。正文按需要说明：

1. **开始条件**：依赖什么已完成结果，用什么证明条件满足。
2. **操作与产物**：改什么模块、配置或资源，预期得到什么。
3. **完成检查**：执行什么检查，看到什么才能勾选完成。
4. **失败处理**：高风险步骤写清何时停止、如何保持或恢复状态。

简单任务可写成一行。多阶段任务按依赖顺序列出；能独立推进的任务可以并行。关键未知项优先调查，避免做到最后才发现产品能力、权限或资源不足。

“开发功能、完善测试、完成验收”不能单独成为可执行任务。通用开发规则不必复制到每一步。开发任务通常写实现位置和行为即可；真实部署操作则需要准确命令或操作入口、目标与成功判据，已有操作手册直接引用。

## 清单、方案与操作记录怎样配合

| 资料 | 保存什么 | 何时需要 |
|---|---|---|
| 设计或 Plan | 批准的目标、方案、边界与验收 | 按项目计划规则判断 |
| 实施清单 | 具体任务、依赖、完成状态、必要的证据链接 | 需要逐步跟进时，可用现有任务系统 |
| 操作手册 | 可以反复使用的操作与恢复步骤 | 有重复运营任务时 |
| 操作记录 | 某次操作的目标、时间、版本、关键动作与实际结果 | 用户要求，或接续、审计、恢复确有需要时 |
| Changelog | 工作流最终验证后的交付结果与遗留限制 | 进入项目的持久化 Plan 生命周期时 |

不要把批准后冻结的 Plan 当成每日进度表。用户需要持续勾选或记录操作时，使用现有任务载体或单独清单；操作记录只保留接续工作所需的事实，原始日志放到项目的证据存储。没有这类需要时，会话中的进度和最终结果说明通常足够。

## 实施前验证条件

按本次操作实际需要，确认目标环境、代码或制品版本、依赖、配置完整性、执行权限和资源条件。对数据写入、迁移、删除等步骤，在执行前确认数据范围、恢复能力及影响窗口。

“有备份”应有可用性证据；恢复风险重要时，应在安全的测试目标验证还原。不可恢复的操作不能用虚构回滚掩盖，应说明不可逆边界和失败后的处理办法。具体执行遵循现有[授权规则](../../.agents/rules/authorization.md)，已有授权范围内的普通工作不重复申请。

## 发布和生效验证

发布证据对应实际版本：记录源代码修订、制品标识以及相关配置版本或非敏感指纹。有构建制品时，尽量在各环境推广同一已验证制品；若重新构建或改变依赖，应重验受影响部分。源码直接部署的项目记录修订、锁定依赖和构建输入。

验证按实际影响分层：

- 构建和静态检查：产物与配置是否合法。
- 测试或演练：核心行为、失败路径和迁移是否符合设计。
- 部署后冒烟：目标版本是否运行，关键依赖与代表性用户路径是否可用。
- 运行观察：本次变更相关的错误、性能和业务结果是否符合项目标准。

有条件时使用小批量或渐进发布，并定义暂停和恢复条件。单节点项目可以采用维护窗口、备份、冒烟检查和观察；不为满足通用规范强制建设复杂发布平台。

发现目标、前置条件或实际行为与方案不符时，先停止依赖这些条件的步骤，记录事实并判断影响范围。检查没有执行、外部行为没有验证，应明确留为缺口，不能勾选通过。

对用户提供服务的实例只运行已推送主分支上的提交，项目声明的先行版渠道除外（见 [deployment.md](../../.agents/rules/deployment.md#pre-release-channels) 的 Pre-Release Channels）。其余从其他分支部署的属于临时部署，开始前写清目的、位置、负责人和结束条件，并按结束条件收尾。推送了会改变运行内容的提交后，尽快提议部署并验证，让失败对得上最近的改动。

## 版本与发布说明

一批新功能或改进收尾、部署完成且发布后检查通过之后，马上在实际运行的提交上打带注释的版本标签；平时推送后的例行部署和先行版渠道的部署不打标签，修复不单独打，随下一个版本发布。版本号由范围内最大的变动决定（见 [releases.md](../../.agents/rules/releases.md#version-numbers) 的 Version Numbers）：破坏兼容面升 MAJOR，新增项目原来没有、作为独立模块或组件交付的功能升 MINOR（先行版渠道这类只改变发布方式的不算），其余升 PATCH。标签说明就是发布说明，按 [releases.md](../../.agents/rules/releases.md) 的七个部分写，Plan 和 Changelog 只链接、不复制。下面是一个示例项目的样例：

```text
v2.3.0 milestone, 2026-10-20, commit 1a2b3c4, previous v2.2.1

Why: 新增备用节点组件：主节点故障时，订阅服务自动切换到它。

How: 见 docs/reviews/feature-failover/plan-failover-2026-10-01.md
和 docs/reviews/feature-failover/changelog-failover-2026-10-19.md。

Scope: 新增 standby 组件，改了 console、subs。v2.2.1..v2.3.0 共 14 个提交，
另含 fix/heartbeat-timeout 的 2 个提交（修复 v2.2.0 引入的心跳超时）
和 3 个文档提交。

Inspect:
  git show v2.3.0
  git log --oneline v2.2.1..v2.3.0
  git diff --stat v2.2.1..v2.3.0
  make status    # 每个实例运行的版本

Verification: 部署后冒烟 6/6 通过；故障切换演练 1 次通过。
缺口：没有演练跨区域网络分区。

Rollback: 目标 v2.2.1。范围内有一次数据库结构变更（新增可空列，
v2.2.1 仍能读取），没有密钥轮换。按 docs/runbooks/rollback.md 执行。
```

说明里不写任何密钥值。打标签和推送标签都需要先给出授权说明；已推送的标签不移动也不删除，打错了就发下一个 PATCH 版本。

## 完成与后续维护

按验收标准确认结果，交代尚未解决的限制、负责人或后续任务。更新仍指导使用的说明，保留需要长期检索的决策与操作证据。历史方案可归档，但入口应指向当前资料；不能因为有了一个新汇总文档就删除仍有独立用途的操作手册或决策依据。

参考：[DORA 部署自动化](https://dora.dev/capabilities/deployment-automation/)、[Google SRE 渐进发布](https://sre.google/workbook/canarying-releases/)。可复制的任务和记录见[简短模板](templates.md)。
