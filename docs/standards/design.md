# 设计规范

设计应让下一位实施者说明白：当前问题是什么，系统会怎样变化，为什么选这个办法，以及如何证明有效。内容要求由 [planning.md](../../.agents/rules/planning.md) 管理；文档归属由 [documentation.md](../../.agents/rules/documentation.md) 管理。

## 先把问题写具体

开头用几句话说明使用者、现有行为、问题和完成后的变化。例如：

> 用户重试创建任务时，系统会生成重复任务。本次让创建入口识别同一个请求：相同请求返回原任务，不再重复创建。

接着说明本次范围、明确不做的内容，以及已有代码或约束。不要用“完善架构、提高可靠性”代替问题。尚未查证的假设，应写清用什么检查确认、在依赖它之前何时确认；不能把目标产品的能力当成已存在事实。

## 说明实现机制和取舍

围绕真正影响实现的内容展开，不要求每次填完整章节：

| 涉及的内容 | 设计需要回答的问题 |
|---|---|
| 模块与系统边界 | 谁负责什么？改动哪些模块？如何与外部服务交互？ |
| 接口 | 输入、输出、错误、权限和兼容性是什么？旧调用方会怎样？ |
| 数据 | 谁拥有数据？约束在哪里保证？并发、重试或部分失败后会怎样？ |
| 配置和策略 | 谁维护、保存在哪里、怎样校验和生效？缺失或非法值如何处理？ |
| 用户操作 | 用户如何完成任务、理解失败、恢复操作？ |
| 安全 | 哪些资产和信任边界受影响？允许谁做什么？如何防止越权？ |
| 性能与可靠性 | 需要保证哪些场景？指标依据是什么？依赖不可用时会怎样？ |
| 部署和迁移 | 新旧版本如何共存？数据如何迁移？出错后能恢复到什么状态？ |

先看现有实现和平台能力。存在有意义的备选方案时，比较收益、复杂度、运维负担和局限；方案明显时直接解释理由，不凑选项数量。对长期影响结构、依赖或接口的决策，已有方案中的说明通常足够；需要跨多个后续任务反复引用时再单独保存 ADR。

跨系统或模块关系用一张局部图通常就够。标出参与者、职责、边界和交互方向；顺序影响正确性时再补时序图。图中的名称应对应项目中的真实实体。无需为了完整而画齐 C4 的所有层级。

## 代码、配置和业务数据各有职责

遵循 [implementation.md](../../.agents/rules/implementation.md) 的单一归属原则：代码实现流程、算法、校验和策略执行；需要由产品或运营调整的取值与策略选择作为数据管理，包括布尔开关、阈值、允许列表和期限。修改频率低，不是把设定写进逻辑的理由。

配置文件、数据库或专用服务的选择，取决于谁编辑、是否需要界面、访问控制、审计、事务和生效方式。每个设定有一个权威来源，其他位置引用或生成。代码中仍可有协议常量和实现细节；可调整性由用途决定，不按“是不是数字或布尔值”判断。

可配置也需要变更控制。设计说明谁能改、如何校验、何时生效、失败时保留什么状态。安全策略的开关同样可以作为数据；其修改权限、审计和无效配置处理由执行逻辑保证。是否允许某个取值，是项目策略决策。

敏感数据沿用[敏感信息规则](../../.agents/rules/secrets.md)。选择加密存储时说明密钥来源、访问权限、轮换与恢复；将数据放进数据库本身不等于完成加密。具体保护目标和宿主环境责任在项目中说明，通用规范不替每个项目选择存储产品。

## 把质量目标变成可验证场景

验收写清“在什么条件下，执行什么动作，应看到什么，用什么证明”。例如：

| 条件与动作 | 应看到的结果 | 验证方式 |
|---|---|---|
| 同一用户以相同请求键和内容重试创建 | 返回同一任务，数据库中只有一条任务 | 接口测试并检查持久化结果 |
| 相同请求键携带不同内容 | 返回冲突，不覆盖原任务 | 错误响应和数据不变断言 |
| 两个请求并发创建同一任务 | 仍只有一条任务，响应符合约定 | 并发集成测试 |

这些是写法示例，不是每个项目的功能要求。性能数值、恢复时限等应来自实际需求和测量，不能为填表而编造。

## 设计评审结束时

检查方案是否足以指导实施：行为和责任明确，关键假设有验证路径，失败与兼容性有交代，验收能够判断成败。仍会影响方向的问题留为明确待决项；一般实现细节由开发者判断。通过设计评审不等于完成代码或获准上线。
