# 完善跨项目工程规范

Status: COMPLETE

结果：[Changelog](changelog-engineering-standards-2026-09-26.md)

## 目标与授权范围

用户要求调查社区资料，完善标准的开发、设计及相关规范；此前已明确通用方法应归 workspace-meta，并授权并行研究。本工作流覆盖一手资料调查、共享规范及中文手册、示例、导航和文档检查的工作树修改与本地验证。

不覆盖项目功能开发、已有项目方案的批准、生产操作、真实主机配置安装或 Git 暂存、提交与发布。写入 workspace-meta 位于当前沙箱可写范围外，需要单独取得运行时技术权限；任务范围已经由用户指定。

## 当前情况

工作区已有规划、实现、文档、评审和验证规则，主要缺少设计的具体表达、可执行任务的写法及部分风险触发检查。之前的项目实施材料混入了通用流程，用户反馈难以阅读。现有授权与文档生命周期继续沿用。

工作树中 project-memory-governance 的已有修改与未跟踪提案属于其他工作，本次保留。

## 方案

1. 查阅 Google 工程实践、arc42、C4、ADR、Diátaxis、Twelve-Factor、NIST、OWASP、DORA 与 SRE 一手资料，记录采用理由和适用边界。
2. 在 `docs/standards/` 提供中文入口、设计规范、开发与评审规范、实施与交付规范、简短模板和来源说明；规则仍由现有 `.agents/rules/` 文件唯一维护。
3. 在既有规则补上具体设计与阶段表达、代码与可调数据、依赖检查、回归与权限拒绝验证、发布证据对应关系。澄清用户要求的清单和操作记录可用，不把每次任务升级为新日志。
4. 更新导航、反向白名单与文档检查范围，验证新目录中的坏链接和不当时效声明可以被发现。

手册只保留必要阅读路径和示例；不建立新的通用审批层、评分体系、每个改动必填的全套文档或重复规则入口。

## 验收与风险

- 读者能找到设计、开发、验证、实施、记录的写法，并理解小改动的简化路径。
- 社区来源与本地选择分开；规范内容不夹带私有项目资料或秘密。
- 共享规则与手册没有冲突，两个代理入口继续使用已有规则路由。
- 文档检查和测试通过；shell 与 Python 语法检查通过；临时环境配置可解析，重复安装不改变已收敛结果。
- 新文件只在精确白名单范围内，预提交保护仍能拒绝范围外文件；真实工作树不暂存。
- 实际落盘前对已有文件做内容一致性检查，保留其他工作；最终说明本地未发布状态及验证局限。

主要风险是扩大流程、制造第二份规则或误改主机配置。通过复用唯一规则来源、按触发条件补要求，以及仅在临时副本验证安装来控制。对于文档可读性，使用具体任务示例并进行独立复核；测试通过不能替代读者判断。
