## 4. 新发现问题

### P1-1：两份 Active 文档的阶段编号互相冲突

协议 §14 定义 Phase 0–6（Phase 0 决策记录、Phase 3 垂直切片）；计划 §4
定义 Phase 0–7（Phase 0 文档收敛、Phase 1 决策记录、Phase 3 安装准备、
Phase 4 垂直切片）。同一个词「Phase 3」在两份当前有效文档中指向不同工作，
「Phase 0」更是一个已执行、一个待执行。后续任何文档或对话引用阶段号都会
歧义，这正是本目录治理试图消灭的那类漂移。

建议：阶段编号只保留一个来源。计划的编号更新且更细，建议协议 §14 改为
「后续阶段以当前 Active plan 为准」并删除或折叠自身编号；或在协议内附
映射表。二选一，不得并存两套。

### P1-2：D09 措辞与协议自身 §7.3 矛盾

D 表 D09 写「长任务承重事实**确认后**尽早持久化」，语序是先确认、后落盘。
§7.3 的规范文本（依前轮 F-04 修正）是反向的：「只有写入和验证成功后，
事实才可以从候选提升为已确认」。D 表是最可能被单独引用的速查层，当前
措辞恰好把 F-04 已纠正的错误重新引入。

建议改为：「长任务承重事实应尽早持久化；写入并验证成功后方可提升为
已确认」。

### P1-3：`operation_key` 无推导规则，§9.2 幂等检查不可实施

§9.2 要求重试前比对「相同 `operation_key`」，但全文对它的定义只有
`reconcile-<stable-operation-key>` 占位符。`run_id` 明确是每次运行新生成
的，而重试（尤其崩溃后的新会话）恰恰是一次新运行——没有确定性推导规则，
重试方无法重建出与上次相同的键，幂等检查的前两条分支永远不会命中。

候选方案（供 Phase 1 采用或否决）：`operation_key` 由稳定输入确定性推导
——作用域 + 目标路径 + 排序后的拟变更 `claim_id` 集合 +（若有）用户任务
标识——并明确排除 `run_id`、时间戳等每次运行变化的成分。

### P2-1：`claim_id` 缺少与 `event_id` 对等的规范

`event_id` 在 §9.1 获得了完整规范（格式、UTC、碰撞检查、不可复用），但
`claim_id` 只有「稳定、不可复用」六个字和 `PM-CLAIM-001` 一个示例。顺序
编号在 §9 防范的同一多 Agent 条件下同样会碰撞；`PM-` 前缀语义、workspace
作用域声明的前缀、创建时的碰撞检查义务均未定义。

### P2-2：D 表内容相对来源草案漂移，且无变更映射

协议 §1.2 沿用了响应文档第 5 节的 D01–D12 编号，但内容有改动而未附映射
说明——最重要的是 D11 从「具体语言待操作者选择」变为「本稿暂以中文作为
工作规范源」，即对一个明确标记为操作者开放项的内容做出了临时决定。§1.2
自己规定「改变基线必须保留废止、替代或映射关系」，这条义务未适用于本次
改动本身。

建议：补一段 D 表相对响应草案的变更清单；D11 标注为「待操作者选择，当前
工作假设为中文」，把决定权明确留在 Phase 1 决策记录。

### P2-3：官方引文仍缺访问日期与章节定位

前轮复审第 4 节修订要求包含「URL、章节、访问日期」。协议 §1.1 只列了
URL。四条引文在 2026-08-08 已经在线核验过（结果记录于响应文档第 4 节），
把已有的访问日期抄入协议是零成本的，不应继续缺失。

### P2-4：未跟踪状态下的历史文档改写不可验证

本轮对六份历史文档的降级改写发生在从未被 Git 跟踪的文件上，没有基线
diff。「只加横幅、未改正文」目前只能靠间接证据支持（行数 +7、关键内容
抽查在）。若后续还有对历史文档的改写轮，建议要么先取得发布授权完成首次
commit 使历史可比对，要么在改写轮的出口证据中记录改写前后的文件哈希。

### P2-5：README 的完整性主张缺少维护义务

计划 Phase 0 出口证据要求「索引存在并列出全部文档」，本轮核验时成立；
但任何新增证据文件都会立刻使其失效——本备忘录就是第一个实例。README
应写明维护规则（新增审查/证据文件时由产出轮同步索引），或把完整性声明
限定到日期。本备忘录遵循目录惯例未修改 README，索引行的补充列为后续
维护动作（见第 5 节）。

### P3（不阻塞，顺带修订）

1. 「推荐」（§6.2、§9.1）不在 §0.2 的五级词汇内，应定义或替换为「应」/「可以」。
2. README 治理条目「中文译文必须标明对应源版本」与 D11「中文为工作源」
   方向矛盾（该方向下英文才是译文），应改为「译文（任何语言）」。
3. history 文件名时间格式 `<YYYY-MM-DDTHHMMSSZ>` 与 `event_id` 的
   `<YYYYMMDDTHHMMSSZ>` 不一致，应统一。
4. §4.3/§4.4 禁止符号链接越出所有者边界，但 12.2 场景集没有对应 fixture；
   建议新增 MGP-14 或扩展 MGP-02/MGP-03 覆盖。

## 5. 建议的修订顺序

进入或伴随 Phase 1 定向复审完成：

1. 统一阶段编号（P1-1）——先做，因为 Phase 1 本身需要无歧义的阶段引用；
2. 修正 D09 措辞（P1-2）；
3. 定义 `operation_key` 推导与 `claim_id` 规范（P1-3 + P2-1，宜同一次
   修订，两者是同一个「标识符规范」问题的两半）；
4. 补 D 表变更映射，D11 恢复为操作者开放项（P2-2）；
5. 补引文访问日期（P2-3）、README 维护义务（P2-5）及 P3 各项；
6. README 新增本备忘录索引行（维护动作，归属下一个修改 README 的轮次）。

以上全部是文本修订，不需要新的运行时、主机或 Git 授权。
