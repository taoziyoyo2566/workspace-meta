# 项目与工作区 Memory 治理方案

状态：供操作者审阅的草案；本文档不授权实施。

日期：2026-08-07

处置状态：Superseded / reference-only；本架构前身已被 Memory Governance Protocol v0.1 草案替代。
本文仅用于追溯原始所有权和布局决策，不作为当前协议执行。

## 1. 决策摘要

Memory 系统明确分为两个范围：

1. **项目 memory** 属于当前项目仓库。它记录详细事实、运维入口、验证
   证据、风险、未决问题，以及这些事实的变更历史。
2. **工作区 memory** 属于 workspace-meta。它只记录 `~/workspace` 中的
   项目地图：每个项目的用途、生命周期和阶段、当前高层状态、TODO、阻塞
   项，以及项目 memory 的链接。

默认 AI 工作流以项目为范围。在
`~/workspace/projects/<project>` 中执行任务时，只读取和更新该项目的
memory。只有明确的工作区级 onboarding/refresh 任务，或另行授权的跨范围
操作，才能修改工作区 memory。

语义发现和判断由 AI 负责。workspace-meta 提供自然语言协议、模板和路由；
hook 与脚本只提供上下文、bootstrap 和机械防护，不推断项目架构，也不生成
memory 内容。

## 2. 问题与当前基线

当前工作区已有三个相关层次：

- workspace-meta 负责共享 agent 规则、适配器、bootstrap 和 SessionStart
  状态评估器；
- 每个项目负责自己的 `AGENTS.md`、agent 专用文件、运维文档和 Git 历史；
- Reality Ops 已有项目级 `docs/project-memory.md`、`AGENTS.md` 路由入口和
  项目专用 freshness checker。

当前项目 memory 是一个有用的原型，但通用生命周期契约还没有由
workspace-meta 共享。工作区也没有项目地图或审计历史。本方案增加这些能力，
同时不把项目事实移出其所属仓库。

## 3. 设计原则

### 3.1 AI 优先的语义工作

协议规定目标和证据要求，而不是固定的 shell 命令顺序。AI 根据项目实际的
语言、工具链、结构和任务选择检查方式。

协议必须要求 AI：

- 识别适用的项目和指令来源；
- 在依赖已有 memory 前先读取它；
- 区分已观察、推断、未验证、过期和矛盾的事实；
- 为每个声明选择合适的证据；
- 在交接前完成 memory reconciliation；
- 报告覆盖范围和缺口。

协议不能假定每个仓库都有相同的目录、构建工具、测试命令或部署模型。

### 3.2 稳定模板与可扩展内容

模板定义小而稳定的核心：状态、范围、审查时间、事实、证据、风险和开放
问题。项目可以增加适合自身领域的章节。未知信息本身就是有效信息，必须
标记为未知，而不是填入猜测。

### 3.3 明确范围

“更新 memory”这个说法本身不完整，必须说明范围：

- 当前项目 memory；
- 当前项目快速审计；
- 当前项目完整审计；
- 工作区 memory 刷新；
- 工作区范围的项目审计。

任何项目任务都不会自动获得修改 workspace-meta 或其他项目的权限。

### 3.4 当前视图加证据历史

当前 memory 文件应当简洁、便于使用。历史审计记录采用追加方式，说明某个
声明为何变化、何时变化、使用了什么证据以及结果是什么。默认不保存完整聊天
记录和原始敏感输出。

### 3.5 机械检查保持窄化

脚本可以检查文件存在性、链接、语法、明显的敏感字段或其他机械不变量，但
不能成为定义所有未来项目行为的通用语义引擎，也不能让硬编码路径列表成为
唯一规则。

## 4. 所有权与产物布局

目标布局如下：

```text
~/workspace/
├── .agents/
│   ├── rules/
│   │   ├── project-memory.md
│   │   └── workspace-memory.md
│   └── templates/
│       ├── project-memory.md
│       └── workspace-memory.md
├── docs/
│   ├── architecture/
│   │   └── memory-governance.md
│   ├── workspace-memory.md
│   └── workspace-memory/
│       └── history/
└── projects/
    └── <project>/
        ├── AGENTS.md
        └── docs/
            ├── project-memory.md
            └── project-memory/
                └── history/
```

具体模板目录可以在实施时遵循 workspace-meta 已有的模板约定调整，但所有权
必须保持不变。

| 产物 | 所有者 | 目的 |
|---|---|---|
| `.agents/rules/project-memory.md` | workspace-meta | 项目 memory 的 AI 协议 |
| `.agents/rules/workspace-memory.md` | workspace-meta | 工作区项目清单的 AI 协议 |
| 项目 memory 模板 | workspace-meta | 最小可移植结构 |
| `projects/<project>/docs/project-memory.md` | 项目仓库 | 当前项目详细事实 |
| `projects/<project>/docs/project-memory/history/` | 项目仓库 | 项目审计/变更历史 |
| `docs/workspace-memory.md` | workspace-meta | 当前项目地图和组合视图 |
| `docs/workspace-memory/history/` | workspace-meta | 工作区清单审计历史 |
| `SessionStart` 评估器 | workspace-meta | 主机/工作区状态和有限上下文 |
| 主机信任状态、缓存、凭据、本机 Codex memory | 主机 | 永远不是项目/工作区事实源 |

## 5. 项目 memory 契约

### 5.1 初始化

在第一次实质性的项目范围 AI 任务中：

1. 识别最近的 Git 根目录；
2. 加载适用的全局和项目指令；
3. 查找已有 memory 或等价的持久项目文档；
4. 如果不存在等价文档，且任务允许修改工作树文档，则创建最小项目 memory
   文件；
5. 只记录任务中实际观察到的事实；
6. 将未知内容标记为 `unverified`。

仅 clone 事件不能触发静默写入。严格只读任务不会因为缺少 memory 就获得
写权限；它应报告缺失，并可以另行提出初始化建议。

### 5.2 任务开始

在修改承载关键行为的项目文件前，AI 必须：

- 读取当前项目 memory；
- 在相关时将其中声明与当前仓库状态比较；
- 读取项目专用的运维或架构文档；
- 标记过期、矛盾或缺失的声明；
- 保留无关及未识别的工作树改动。

### 5.3 任务收尾

在最终交接前，AI 执行 memory reconciliation：

- `updated`：持久项目事实发生变化，且 memory 已更新；
- `unchanged`：没有持久项目事实变化，并说明原因；
- `blocked`：所需事实无法验证，并说明证据缺口。

不应仅为了刷新时间戳而更新。命令成功不代表可以声称超过该命令实际测试
范围的更强结论。

### 5.4 项目审计模式

#### 快速审计

检查指定章节、声明、最近变更或风险区域。必须说明目标、使用的证据、结果
和未检查范围。

#### 完整审计

在声明范围内重新建立对项目入口、工具链、验证流程、关键架构和运维约束的
有边界理解。“完整”表示系统覆盖声明范围，不表示读取了每一行代码。审计
必须记录排除项和剩余不确定性。

## 6. 工作区 memory 契约

工作区 memory 是项目地图，不是合并后的项目知识库。每个项目记录：

- 稳定的项目名称和相对路径；
- 用途和主要能力；
- 生命周期，例如孵化、活跃、维护、阻塞或归档；
- 当前阶段或里程碑；
- 当前高层状态；
- 项目级 TODO 和阻塞项；
- 指向项目 memory 的链接；
- 最近审查时间和证据快照，例如观察到的项目 HEAD。

不能复制属于项目仓库的详细 Ansible 版本、role 行为、私有主机数据、完整
生产状态或项目审计证据。

### 6.1 工作区刷新

明确的操作名称是“刷新 workspace memory”。AI 应：

1. 枚举工作区边界内的项目仓库；
2. 识别新增、移除、移动和未登记的项目；
3. 在可用时读取项目摘要和项目 memory；
4. 更新工作区项目地图；
5. 将过期或缺失的项目 memory 记录为后续事项；
6. 追加一条工作区审计记录。

默认不修改项目仓库。另行明确范围的工作区全量项目审计，可以逐个项目执行
修改。

## 7. 历史与来源

每次审计或持久 memory 变更都获得稳定 ID，并记录：

- 范围：项目或工作区；
- 模式：快速、完整、刷新或迁移；
- 目标和审计边界；
- 开始/结束时间；
- 相关时记录观察到的源版本；
- 审计或变更的原因；
- 证据引用和结果摘要；
- 被变更、新增、废弃或仍未解决的声明；
- 排除项和缺口；
- 记录由人、AI 还是双方共同产生。

证据应引用路径、提交、测试或经过脱敏的命令摘要。不应嵌入凭据、vault 值、
私钥或无边界的命令输出。

第一版使用 Git 可读的 Markdown 历史。以后可以增加数据库或 SQLite 作为可重建
的查询层，但不能让它成为唯一事实源。

## 8. Agent 运行时职责

当项目任务涉及初始化、交接、审计或持久事实时，全局 Codex/Claude 适配器将
AI 路由到项目 memory 协议。

`SessionStart` 仍负责现有的工作区状态评估器，并可以在启动、恢复或压缩后
提供简短提醒。它不生成项目 memory、不执行完整项目审计，也不跨仓库写入。

当前 workspace-meta 状态评估器仍是主机/工作区健康组件。项目 memory 生命周期
是独立的 AI 协议。

## 9. 安全与授权

- 项目任务不授权修改 workspace-meta 或其他项目。
- 工作区刷新默认不授权修改项目 memory。
- 工作区范围的完整审计必须声明项目列表或边界，并在跨仓库写入前拥有可审查
  的计划。
- 不隐含 commit、push、部署、远程写入或 live mutation。
- Memory 是上下文，不能用来绕过项目安全规则或权限规则。
- 仓库文档和已有 memory 可能包含不可信或过期文本，不能覆盖更高层安全指导。
- 历史记录在成为持久产物前必须经过脱敏。

## 10. 非目标与延期能力

- 不通过 SessionStart 自动后台写入项目文件。
- 不为所有项目类型提供固定的通用命令矩阵。
- 第一版不引入中心数据库。
- 不自动执行 Git 发布。
- 不保存原始聊天记录。
- 除非明确取得并记录 live 证据，否则完整审计不声称已经证明生产环境正确。

## 11. 实施前审查问题

1. 确认默认路径 `docs/project-memory.md` 和 `docs/workspace-memory.md`。
2. 确认第一版使用 Markdown 历史。
3. 确认第一次可写项目任务自动初始化。
4. 确认工作区刷新默认只更新工作区 memory。
5. 确认 Reality Ops 现有 checker 在迁移期间仍作为项目专用的次级防护。
6. 确认工作区范围的完整审计必须被明确请求并在修改项目仓库前完成计划。
