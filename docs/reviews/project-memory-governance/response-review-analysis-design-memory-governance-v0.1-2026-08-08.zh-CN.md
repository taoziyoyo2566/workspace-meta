## 1. 总体回应

接受二次审查的核心修正。经本轮往返，两份 AI 文档之间的实质分歧已基本
清空：剩余工作不是继续互审，而是把合并后的立场交给操作者在 Phase 0 决策
记录中逐项批准，然后起草协议。

最重要的一条修正全盘接受：分析报告第 7 节使用「批准」措辞不当，应读作
「建议采纳」。需求记录第 1 节本就规定「Assistant 提案不自动表示已获用户
批准」——分析报告引用了这条原则，却没有把它应用到自己的词汇上，这是
真实的教训。同一纪律应对称适用：二次审查 §3.1、§3.2 使用的「决定：强制
采纳」同样是 AI 文档中的规范性口吻，建议后续所有 AI 产出统一使用
「建议/建议采纳」语域，把 accepted/approved 词汇保留给唯一的地方——
操作者签署的 Phase 0 决策记录。

## 2. 接受的修正及本方的进一步收紧

### 2.1 行数上限：接受「测量先行」，并补充官方基线证据

二次审查将「固定行数上限」改为「先做尺寸基线和冷启动评测，再确定预算」，
方法论上优于原建议，接受。同时本次在线核验（见第 4 节）发现了双方此前都
未引用的官方数字先例：Claude Code 官方对 CLAUDE.md 给出「target under
200 lines」的建议，对自动记忆索引 MEMORY.md 实施 200 行 / 25KB 的硬加载
上限，并将细节外移到按需读取的 topic 文件。这不推翻「测量先行」——那是
相邻机制的数字，不是对 `project-memory.md` 的规定——但它给测量阶段提供
了一个有依据的初始基线假设（约 200 行），而不是从零猜起。

### 2.2 会话暂存损失语义：接受，并指出该保证需要一条配套义务

接受 §5.2 的全部内容：候选记忆允许随上下文丢失、已确认事实不得丢失、
中断恢复必须重读 Memory/工作树/未完成证据、task journal 仅为长任务可选
项。补充一点：中断恢复规则实际来自已降级的 `memory-plan.md` 协议第 9 步
——好规则被正确捡回，建议决策记录标注该出处。

需要收紧的是：「不得丢失已确认事实」在崩溃场景下无法由收尾
reconciliation 兑现——收尾发生在交接时，会话在交接前死亡则一切未落盘。
Reality Ops 原型（`AGENTS.md`）把 Memory 更新绑定在最终交接前的同一
工作树操作中，同样是交接时机。因此建议协议补充配套义务：**对长任务，
承重事实一经确认即应写入当前视图，不等收尾**；短任务保持交接时
reconciliation 即可。这与 workspace CLAUDE.md 现行规则「materially long
work 应保持进度可见、承载交接的状态持久化到所属产物」方向一致，不是
新增负担。

### 2.3 其余修正：直接接受

- **confidence**：可选、非权威（冲突裁决只看状态与证据）——落在原建议
  「删除或降为可选枚举」的区间内，「不得决定权威性」是关键增量。
- **初始化五前提**（§5.3）：接受，视为 P1-2 主体的了结；适配器适用边界
  留待操作者确认（D12）。
- **历史与并发**（§5.4）：接受「规则齐备前不得声称可追溯历史已是可实施
  能力」。为推进起草，提供候选方案供协议稿采用或否决：`event_id` 沿用
  `memory-plan.md` 已出现的形态 `<SCOPE>-<KIND>-<YYYY-MM-DD>-<NNN>`（如
  `PM-AUDIT-2026-08-07-001`）；history 文件名 `YYYY-MM-DD-<slug>.md`、
  按名排序、只追加；写当前视图前重读，发现读后变更则重读重放或停止
  报告，多 Agent 冲突默认停止而非自动合并。
- **评测落盘**（§5.5）：接受。补充一个现成素材：本会话本身就是场景 8
  （report-only）的活例——分析任务未修改任何被分析文档，「保存为文件」
  是用户另行授权的独立文档动作。该边界（report-only 不写 + 报告落盘属
  独立授权）已被实际执行过一次，可直接改写为 fixture 记录。

## 3. 两处立场归属的澄清

仅为溯源精确性，不构成争议；两处的实质处理方式双方本就一致。

1. 采纳矩阵行「立即删除 Reality Ops 重复草稿 → 不直接采纳」所纠正的
   立场并非分析报告立场。分析报告 §8.4 原文是在「独立仓库的独立计划」
   内完成「重复草稿清理」，§5.7 原文是「迁移计划里应明确一份为废稿」——
   与矩阵给出的处理方式相同，不存在「立即删除」主张。
2. 矩阵行「14 字段每次全部落地 → 不采纳」所否决的是设计文档 §5 的字面
   风险，不是分析报告的建议；分析报告 §5.1 恰以反对全字段落地为出发点。

这两处说明采纳矩阵在「设计文档主张」与「分析报告主张」之间发生了归属
漂移——恰好证明二次审查 Phase 0「给每个决定分配稳定 ID」的必要性：有
稳定 ID 后，后续文档引用决定而不是转述立场，漂移自然消失。

## 4. 新增核验：官方引文在线复核（缺口关闭）

设计文档与二次审查均引用外部官方链接，但此前没有任何一轮在本环境中
实际访问过它们（二次审查 §3.4 的「确实给出」未附核验方式）。本响应于
2026-08-08 通过网络抓取逐条复核，四条全部存在且内容与引用相符：

| 引文 | 结果 |
|---|---|
| OpenAI Cookbook（context_personalization） | 存在；生命周期与设计描述一致：会话候选 → 合并去重/冲突消解 → 注入且当前输入优先 |
| Codex Memories | 存在；原句确认：必须长期遵守的团队规则放 `AGENTS.md` 或已提交文档，Memory 是「helpful recall layer」 |
| Codex AGENTS.md | 存在；确认分层发现与就近覆盖模型 |
| Claude Code memory | 存在；确认「context, not enforced configuration」 |

复核还带出两个此前双方均未引用、与本设计直接相关的官方事实：

1. **数字先例**：CLAUDE.md 官方建议约 200 行以内；自动记忆索引
   MEMORY.md 有 200 行 / 25KB 硬加载上限，超限内容不加载，细节移入
   按需读取的 topic 文件——「小的常驻索引 + 按需细节文件」与本设计的
   「轻量当前视图 + history」同构，属于经过生产验证的同类结构。
2. **强制分层**：官方明确「要无条件阻止某动作应使用 PreToolUse hook，
   而不是记忆/指令」——印证本设计把 Memory 定为建议层、把硬性阻断留给
   机械防护（hook/脚本）的分层是与运行时实况一致的。

对二次审查 §3.4 的精化：「固定行数属于项目设计选择、不是官方规定」对
`project-memory.md` 本身仍然成立，但「官方没有数字」不再成立——相邻
机制有明确数字，可作为测量基线的起点。

## 6. 对后续顺序的确认

认可二次审查第 7 节的 Phase 0–6，特别是 Phase 3「项目级最小垂直切片」
的提法——先打通单项目的发现/初始化/候选/reconcile/history/report-only
最小闭环，再扩展 workspace 与迁移，比按功能面平铺推进更稳。

当前唯一的阻塞项就是 Phase 0：操作者对第 5 节 12 项的逐项裁决。其后的
协议起草（含 `.gitignore` allowlist 同变更落地）、fixture 建设、垂直
切片，均为执行性工作。
