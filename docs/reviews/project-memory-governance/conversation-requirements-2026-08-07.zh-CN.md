## 1. 本文件的目的

本文件保存用户的原始意图、后续修正、已接受约束、被否决的解释和未决决定，使方案和实施计划可以根据对话进行审查，而不是只能依据 assistant 的最终摘要判断。

记录区分四类陈述：

1. **用户需求**：用户表达的目标、担忧或修正。
2. **已确认方向**：经过后续审查、已经体现在当前设计中的方向。
3. **Assistant 提案**：用于讨论的想法，不自动表示已获用户批准。
4. **开放决定**：实施前仍需明确审查的选择。

用户的修正优先于更早的 assistant 提案。当前仓库事实是实施规划的证据，不替代用户要求的范围。

## 2. 起始背景与动机

对话起始于 Reality Ops 项目的运维问题：

- Ansible syntax-check 无法可靠运行；
- 不清楚项目是否配置了 Python virtual environment；
- 用户要求将 venv 配置写入 setup，验证 venv，并将 Ansible 运维信息放入项目 memory，供未来 AI 会话使用。

这引出了更宽的问题：AI agent 应如何保留和刷新项目专用运维知识，而不依赖用户记忆或脆弱的主机本地状态？

这里的运维动机很重要：memory 旨在帮助未来的 AI agent 理解如何操作真实项目，但不能替代当前配置、当前命令输出或 live verification。

## 3. 用户需求与反馈的时间顺序

### 3.1 项目状态与 Ansible 工具链

#### 用户意图

用户首先询问当前项目状态，以及 Ansible syntax-check 无法运行的原因，包括是否缺少或未配置 venv。

#### 推导出的需求

项目需要一个可复现、由项目拥有的工具链入口，而不能依赖主机全局 Ansible 或隐式激活的 venv。

#### 后续影响

项目方案引入了 setup、setup.conf、配置好的 venv、Ansible/collection 验证，以及描述受支持调用路径的项目 memory 条目。这是项目专用实施背景，不是工作区级 memory 需求。

### 3.2 将运维知识放入项目 memory

#### 用户意图

用户要求把 Ansible 相关信息写入项目 memory，使后来的 agent 能自动知道如何处理这类操作。

#### 推导出的需求

项目 memory 必须记录可执行的交接知识，例如：

- 哪个 setup 入口是权威入口；
- 如何选择 venv 和 Ansible 工具；
- 用什么命令验证控制节点；
- syntax-check 和功能检查分别意味着什么；
- 哪些结果只是环境缺口；
- 哪些运维操作存在安全限制。

#### 边界

项目 memory 是带日期的证据和交接产物，不是配置、代码或当前 live 状态的事实源。承载关键行为的声明在使用前必须重新检查。

### 3.3 问题：项目 memory 应放在哪里？

#### 用户担忧

用户询问项目级 memory 是否应该放在 docs 下。

#### 得出的方向

可以使用 docs/project-memory.md 之类的项目文档，前提是：

- 它属于项目仓库；
- 项目的 agent 入口会读取它；
- 它不会与主机本地 Codex memory 混淆；
- 它不会替代项目规则或可执行配置。

### 3.4 自动识别与更新

#### 用户需求

用户不希望自己记住每次都要告诉 agent memory 在哪里或何时更新。agent 应在适当时自动识别和更新项目 memory。

#### 重要解释

“自动”表示 AI 遵循一个持久的项目工作生命周期协议，而不是后台进程在没有任务范围或写入权限的情况下静默改写项目文件。

### 3.5 实时或周期更新

#### 用户问题

用户询问 agent 会实时更新 memory，还是按固定时间间隔更新。

#### 得出的方向

不需要连续或定时更新。合理的更新边界是任务生命周期：

~~~text
任务开始 → 读取/重新检查相关 memory
任务进行 → 收集新证据
任务结束 → 对持久事实进行 reconciliation，并在需要时更新
~~~

时间可以作为证据元数据记录，但不能仅因为时间流逝就让 AI 发明新事实或改写时间戳。

### 3.6 每次代码提交都更新

#### 用户问题

用户询问是否每次代码 commit 都应更新 memory。

#### 得出的方向

不应为每次 commit 重写 memory。commit 可以触发审查，但不能证明必须更新 memory。

关键问题是变更是否产生或使某个持久项目事实失效，例如：

- 工具链或入口发生变化；
- 架构或运维行为发生变化；
- 验证方法发生变化；
- 新增风险或已知限制；
- 项目阶段或 TODO 发生变化。

普通格式化变更可以合理地得到“memory unchanged”。

### 3.7 最佳实践规则设计

#### 用户需求

用户要求按最佳实践设计 memory 更新规则。

#### 已确认方向

规则应结合：

- 持久的 AI 指令；
- 项目拥有的事实型 memory；
- 基于证据的更新；
- 明确的缺口和不确定性；
- 可选的机械检查；
- 不自动执行 Git 发布。

规则必须保留无关工作，不得暴露 secrets 或完整用户记录。

### 3.8 将治理移到 workspace-meta

#### 用户担忧

用户观察到规则本身更适合放在工作区级别，使新机器或新项目都能继承相同行为，并询问是否应将规则移到 workspace-meta。

#### 得出的方向

是的，**协议和模板**属于 workspace-meta；**项目事实和项目 memory**仍属于各自项目仓库。

这是两级所有权模型：

~~~text
workspace-meta → AI 如何管理 memory
项目仓库      → 项目实际知道什么
~~~

workspace-meta 不能成为项目专用运维事实的中央所有者。

### 3.9 新设备、新项目或 clone 的项目

#### 用户提议

新设备使用 workspace-meta 后，如果新建或 clone 项目并在其中使用 AI，agent 应自动创建该项目的 memory 记录。

#### 确认后的解释

第一次实质性的项目范围 AI 任务必须检查已有 memory。如果不存在等价的持久项目 memory，且任务允许修改工作树文档，AI 就初始化最小 memory 文件。

初始化必须：

- 使用共享模板；
- 只记录实际观察到的事实；
- 将未知内容标记为 unverified；
- 如果已有 memory 格式，则保留它；
- 避免创建重复 memory 文件。

仅发生 clone 不能触发静默写入。严格只读任务不能仅因缺少 memory 就获得写权限；它必须报告缺口，并可另行提出初始化建议。

### 3.10 可以使用模板，但不能使用固定语义脚本

#### 用户修正

用户明确质疑通过固定脚本实现。AI 能力和项目结构会变化，硬编码当今项目类型和命令的脚本可能很快过时。

用户更倾向于给 AI 清晰的目标指令，同时允许 AI 自己判断具体方法。

#### 已确认方向

workspace-meta 可以提供：

- 自然语言协议；
- 稳定模板；
- 证据和状态字段示例；
- 通过全局 agent 指令进行路由。

workspace-meta 不应提供一个决定项目架构、选择所有检查命令或生成语义 memory 内容的通用脚本。

脚本仍可以用于：

- bootstrap 和主机配置收敛；
- SessionStart 状态报告；
- 链接/路径检查；
- 语法和明显格式检查；
- 明显的 secret 安全防护；
- 项目有意保留的更严格项目专用 gate。

### 3.11 重新考虑 SessionStart

#### 用户担忧

用户认为 SessionStart 可能不是 memory 管理的正确机制，并询问为什么不让 AI 自己完成这些工作。

#### 已确认方向

SessionStart 不是语义 memory agent。它可以：

- 在启动、恢复或压缩后恢复一条简短提醒；
- 报告工作区健康状态；
- 在可以机械判断时报告 memory 缺失或过期。

项目发现、证据选择、memory 初始化、声明评估和历史写入必须由 AI 完成。SessionStart 不能成为隐藏的跨项目写入器或完整仓库审计器。

### 3.12 AI 生命周期协议

用户审阅了九步 AI 协议并要求进一步验证。协议稳定内容是：

1. 识别当前 Git 根目录和适用规则；
2. 查找已有 memory、runbook、README 和 agent 指导；
3. 在项目没有 memory 且写入属于任务范围时初始化最小 memory；
4. 在依赖 memory 前读取它；
5. 重新检查承载关键行为的事实；
6. 判断持久项目事实是否发生变化；
7. 根据实际证据更新 memory；
8. 不仅为刷新时间戳而重写 memory；
9. 永远不允许 memory 覆盖安全规则、权限、配置或当前验证结果。

后续修正是：初始化不应依赖主观的“项目是否值得拥有 memory”判断。第一次可写的实质性项目任务是默认初始化边界。

### 3.13 手动刷新与审计

#### 用户提议

用户提议提供手动的全局更新能力。memory 变旧后，用户可能不再信任它，希望 AI 检查 memory 是否仍然真实。

用户至少提出两个级别：

- 对 memory 某一部分进行快速、聚焦的检查；
- 对完整代码库/项目进行调查。

#### 已确认方向

默认手动审计范围是当前项目：

~~~text
快速审计 → 指定声明/章节/风险区域
完整审计 → 对当前项目进行有边界的系统性审查
~~~

AI 必须报告：

- 审计范围；
- 使用的证据；
- 已确认或变更的声明；
- 排除项；
- 未解决的缺口；
- 最终产生的 memory 更新。

“完整”表示对已声明范围进行系统覆盖，不表示错误地声称读过每一行代码或证明了所有 live 资源正确。

### 3.14 类数据库的 memory 与历史

#### 用户提议

用户提出类似数据库的 memory 系统，用于保存修改历史，包括：

- 某个 memory 条目为什么变化；
- 何时变化；
- 结果是什么；
- 哪些证据提高或降低了可信度；
- 类似客户需求记录的过程历史。

#### 已确认方向

概念模型是：

~~~text
当前 memory 视图 + 追加式证据历史
~~~

当前 memory 保持简洁、有用。历史记录审计运行和声明变化。第一版应使用 Git 可读的 Markdown 或其他按行组织的格式。以后可以引入数据库或 SQLite 作为可重建查询层，但不能成为唯一事实源。

历史应记录证据摘要，而不是原始聊天记录或敏感命令输出。

### 3.15 工作区级 memory 的修正

#### 用户修正

assistant 曾提出“审计工作区下所有项目”。用户修正了范围：如果存在工作区级审查，它应产生**工作区级 memory**，而不是把所有项目 memory 合并在一起。

工作区 memory 应记录：

- 工作区中有哪些项目；
- 每个项目实现什么；
- 每个项目当前处于什么阶段；
- 当前高层状态；
- TODO 和阻塞项；
- 项目 memory 链接。

#### 已确认方向

两个范围如下：

| 操作 | 默认目标 |
|---|---|
| 普通项目任务 | 当前项目 memory |
| 当前项目快速/完整审计 | 当前项目 memory 和历史 |
| 工作区 memory 刷新 | 工作区项目地图和工作区历史 |
| 工作区范围的项目审计 | 明确的多项目操作；项目修改需另行确定范围 |

普通项目任务默认不得更新工作区 memory。工作区刷新默认不得修改项目 memory。

### 3.16 要求可审查的方案和实施文档

#### 用户需求

用户要求先用 Markdown 写出详细方案和实施计划，说明实际操作和预期效果，以便在实施开始前进行审查。

#### 已确认流程

必须先写文档，再实施。实施等待审查和批准。计划必须包含：

- 范围和排除项；
- 仓库事实和假设；
- 具体文件和阶段；
- 预期效果；
- 验证方式；
- 验收标准；
- 风险；
- 回滚和交接行为。

### 3.17 要求审查对话漂移

#### 用户需求

用户要求回顾对话，因为 assistant 之前曾引入范围漂移和互相矛盾的摘要。

#### 已确认流程

对话本身记录在本文件中，以便比较：

- 原始需求；
- assistant 提案；
- 用户后续修正；
- 当前方案文档；
- 当前实施计划。

## 4. 汇总需求

以下需求应视为稳定需求，除非用户明确修改：

### R1 — 项目优先的默认范围

项目任务的正常目标是项目 memory。当前项目不会自动扩大为整个工作区。

### R2 — workspace-meta 拥有协议

workspace-meta 拥有可复用的自然语言规则、模板、适配器和工作区项目清单，但不拥有项目专用事实。

### R3 — AI 拥有语义决策

AI 决定如何调查、哪些证据相关、哪些内容应被记住，以及声明是已验证、过期、矛盾还是未知。

### R4 — 模板化但不固定语义脚本

核心 memory 结构标准化，但项目和未来 AI 版本可以扩展内容。没有通用脚本定义项目语义。

### R5 — 第一次可写项目任务初始化 memory

AI 必须检测 memory 是否缺失，并在当前任务允许修改项目文档时初始化最小项目记录。

### R6 — 任务收尾 reconciliation

交接前，AI 必须明确选择 memory 状态：updated、unchanged 或 blocked。

### R7 — 手动项目审计

快速和完整审计是对当前项目执行的明确 AI 操作，并记录范围、证据、结果和缺口。

### R8 — 工作区摘要 memory

工作区 memory 记录项目地图、项目用途、阶段、状态、TODO、阻塞项和链接，不是合并的技术 memory。

### R9 — 历史与来源

持久变更记录原因、时间、证据、结果和未解决的不确定性。第一版历史使用 Git 可读文本，数据库延期。

### R10 — SessionStart 是辅助机制

SessionStart 可以提醒和报告，但不执行语义 memory 管理，也不静默写入项目文件。

### R11 — 明确的跨范围授权

工作区刷新和工作区范围的项目审计是不同操作。跨项目写入需要明确范围和可审查计划。

### R12 — 不自动发布

Memory 实施、审计和刷新不意味着 Git stage、commit、push、PR、部署或 live mutation。

## 5. 被否决或被替代的解释

### A. “Memory 只是脚本生成的状态文件”

否决。脚本无法跟上项目差异和 AI 能力变化，语义调查和写入必须由 AI 负责。

### B. “每次 commit 都必须重写 memory”

否决。commit 可以触发审查，但只有持久事实发生变化时才需要更新 memory。

### C. “SessionStart 执行完整项目审计”

否决。SessionStart 是生命周期/上下文机制，不是推理 agent。

### D. “每个项目自己决定是否值得拥有 memory”

已替代。默认在第一次可写的实质性项目任务中初始化最小 memory。只读例外是写权限问题，不是项目价值问题。

### E. “工作区审计直接重写每个项目 memory”

作为默认行为否决。工作区刷新更新工作区 memory，并记录哪些项目 memory 需要审查。跨项目项目-memory 修改需要明确范围。

### F. “一个中心数据库拥有所有项目 memory”

第一版延期/否决。各项目 Git 产物仍是权威来源，后续数据库只能作为可重建索引。
