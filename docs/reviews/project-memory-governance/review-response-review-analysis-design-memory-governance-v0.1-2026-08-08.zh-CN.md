## 1. 总体结论

被审查文档是一份质量较高的“审查响应与 Phase 0 决策输入”，但还不能
作为“最终审查已经闭环”或“可以直接实施”的结论。

它正确完成了三件事：明确 AI 文档不能代替操作者批准；承认此前把“建议
采纳”写成“批准”的问题；把会话丢失、历史并发、评测落盘等缺口重新带回
讨论范围。

但它把“审查意见已合并”进一步表述成“实质分歧已基本清空”，并称 Phase 0
是“唯一的阻塞项”。这个判断过早。Phase 0 是授权决策的门槛，不是唯一的
技术闭环门槛；协议的可执行细节和评测证据仍未完成。

## 2. 需要修正的主要问题

### F-01：结论对剩余缺口的描述过强（P1）

文档第 1 节称两份 AI 文档之间的实质分歧已基本清空，第 6 节称当前唯一
阻塞项是操作者对 12 项草案的裁决。

但同一份文档仍明确存在以下未决内容：

- D02 的事件 ID、追加和并发方案仍只是“候选方案”；
- D09 中“长任务承重事实确认即写”是新增且待评审的内容；
- D11 的规范语言尚未确定；
- D05 属于独立 Reality Ops 仓库的项目决策；
- 路径发现、持久化失败、幂等重试、当前视图与 history 一致性仍没有完整协议。

建议将结论改为：

> 二次审查意见已经合并为候选决策输入，但设计仍未达到实施批准条件。
> Phase 0 是操作者授权门槛，后续仍需完成协议细化、fixture 评测和适配器
> 边界确认。

### F-02：12 项草案尚未达到可执行决策记录的粒度（P1）

D01–D12 有助于集中讨论，但内容层级不一致，且缺少执行所需的上下文：

- D03 引用其他文档中的“五前提”，没有在本表中复述具体规则；
- D04 没有规定自定义路径的发现顺序、规范声明格式、符号链接和多候选
  处理算法；
- D08 说“最小 5 字段”，但没有列出字段名称、状态值和示例；
- D09 没有定义“长任务”、写入成功的判定、写入失败时的行为；
- D10 没有定义 TTL 重验失败后的处理和报告格式。

正式决策记录至少应为每一项补充：状态、选项、被选方案、理由、范围、
责任人、前置条件、验收标准和回滚/废止方式。当前使用“草案 ID”，并把
最终 ID 方案留到之后确定，也会削弱后续文档的稳定引用；应保留不可变 ID，
或提供旧 ID 到正式 ID 的映射表。

### F-03：history 和并发规则仍没有形成可实施保证（P1）

示例 `PM-AUDIT-2026-08-07-001` 不能单独保证多 Agent、重试或并行任务下的
唯一性。按日期和 slug 排序、只追加，也没有解决以下问题：

- 并行执行者如何获得唯一事件 ID；
- 重试是否幂等；
- 当前视图写入和 history 追加是否需要一致性保证；
- 写前重读后如何检测读后变更；
- 冲突、停止和恢复报告采用什么格式。

协议至少需要明确运行实例或执行者标识、源文件版本/摘要、重复事件处理、
乐观并发检查、冲突停止条件和人工恢复流程。在这些规则确定前，不应声称
history 已经提供可追溯能力。

### F-04：“已确认事实不得丢失”仍是未经定义的能力承诺（P1）

文档提出长任务中承重事实一经确认就写入当前视图，这是比仅在收尾时写入
更可靠的方向。但写入当前视图不等于已经保证“不丢失”：写入可能失败，
进程可能在确认和落盘之间退出，工作树也可能存在未提交状态。

建议把状态转换定义为：只有持久化写入成功并被验证后，事实才进入“已确认”；
否则仍是候选或待恢复状态。写入失败必须可见地报告，且 report-only 模式
不得因为“确认事实”而隐式产生写入副作用。

### F-05：官方资料的证据链不够可复现，且有一处推断过度（P1）

第 4 节声称已在线复核四条官方引文，但表格没有提供具体 URL、章节定位、
访问时间或对应结论的原文范围，因此独立读者无法从该备忘录复核“缺口关闭”。

官方资料确实支持相近事实：

- [Claude Code Memory](https://code.claude.com/docs/en/memory) 描述了记忆索引
  的 200 行/25KB 加载边界，也明确记忆属于上下文而非强制配置；
- [OpenAI Cookbook：Context Personalization](https://developers.openai.com/cookbook/examples/agents_sdk/context_personalization)
  描述了会话记录、合并、去重、冲突处理和注入评测；
- [Codex Memories](https://learn.chatgpt.com/docs/customization/memories)
  明确长期必须遵守的团队规则应放在 `AGENTS.md` 或已提交文档中，Memory
  只是辅助回忆层。

这些资料可以作为设计参考和初始假设，但不能推出本项目方案“已经经过生产
验证”。尤其 Claude Code 的自动 Memory 是机器本地机制，而本项目设计的是
受 Git 和项目治理约束的共享文档；两者结构相近，不代表适用性已经被证明。
建议将“经过生产验证的同类结构”改为“官方文档描述的相近结构，可作为待评测
的初始假设”。

### F-06：通用协议和本地适配器仍有混杂（P2）

D05 的 Reality Ops checker 和 D12 的 `~/workspace` 范围是本地适配器或项目
治理决策，不应直接与通用 Memory 协议放在同一层级。

建议拆成三组：

1. 通用 Memory 协议决策；
2. workspace-meta 的 v0.1 适配器范围；
3. Reality Ops 独立仓库的迁移和 checker 决策。

这样既能保留 Ansible/Reality Ops 作为引子和验证场景，也不会让通用方案
被 `~/workspace` 的当前目录结构绑定。

### F-07：场景 8 还是案例，不是评测闭环（P2）

本次会话没有修改被审查文档，能够作为 report-only 行为的案例。但它还没有
形成可重复 fixture，因为缺少固定输入、预期结果、实际结果、通过/失败判定、
审核者和证据文件。

因此它可以作为 fixture 的素材，不能作为已经关闭评测缺口的证据。至少还应
补充冷启动、候选写入、冲突合并、过期重验、敏感内容拒绝、并发冲突和中断
恢复场景。

### F-08：状态词汇虽已纠正原则，正文仍有混用（P2）

文档正确指出 AI 产出不应使用“批准”替代操作者决策，但正文仍大量使用
“接受”“认可”“了结”“缺口关闭”“唯一阻塞项”等容易被下游执行者理解为
已经定案的词汇。

建议统一使用：

- “审查意见：建议采纳”；
- “候选决策：待操作者确认”；
- “技术状态：未闭环”；
- “证据状态：已核验/部分核验/未核验”。

## 3. 可保留的内容

以下内容值得保留并进入后续决策记录：

- 明确 AI 文档不能替代操作者批准；
- 保留 report-only 与 reconcile 的区别；
- 当前视图轻量化、详细信息进入 history 的方向；
- 记忆不能覆盖安全、权限和当前用户意图；
- 长任务需要更早持久化承重进度；
- 在协议规则、并发和评测明确前，不声称 history 已可实施；
- 对未运行测试、未执行 bootstrap 和未进行 Git 发布保持诚实披露。

## 4. 作为 Phase 0 输入前的必要修订

建议至少完成以下修订后，再把该文档提交给操作者逐项决策：

1. 将“实质分歧已基本清空”和“唯一阻塞项”改为“审查意见已合并，但仍有
   技术未决项”；
2. 给 D01–D12 增加状态、责任人、验收标准和依赖关系；
3. 在文档内列出 D03 的初始化前提、D08 的五个字段和 D09 的失败语义；
4. 增加官方资料 URL、章节、访问日期和“事实/推断”区分；
5. 把通用协议、workspace-meta 适配器和 Reality Ops 迁移决策拆开；
6. 把场景 8 改写成固定 fixture，并补充最小评测结果格式；
7. 统一“建议采纳/待确认/未闭环”等状态词汇。

## 5. 最终判定

本备忘录的判定为：**可保留，需修订；暂不批准实施**。

被审查文档适合作为下一轮 Phase 0 决策的输入，不适合作为协议已定稿、
技术缺口已全部关闭或可以立即修改 `.gitignore`、创建协议文件、迁移 Reality
Ops 文档的授权依据。

本次仅新增本复审备忘录，未修改被审查文档、设计文档、Reality Ops 仓库或
任何 Git 发布状态。
