## 1. 总体判定

原审查文件的总体方向正确：当前 Protocol Draft 可以保留为候选工作来源，适合进入定向复审，但不应据此进入安装、运行时实现或项目迁移。其识别出的三个 P1 问题均能从当前协议和计划正文直接复现，应采纳；P2、P3 问题大部分也成立。

本次复审补充发现两个需要纠正的报告层问题：

1. 原审查文件把 README 的完整性描述为「16 个相对链接 + README 自身 = 目录 17 个文件全覆盖」。原审查文件写入后，目录实际已有 18 个 Markdown 文件，README 仍只有 16 个不重复的 Markdown 链接，且原审查文件自身没有被索引。因此该结论只是过时的时间点快照，不能作为原审查文件写入后的当前状态结论。
2. 原审查文件第 1 节称 F-01–F-08 中「六项已落实、两项显式推迟」，但第 3 节明细同时标出 F-02、F-03、F-04、F-05、F-08 的部分落实或残留问题，F-07 也明确只是「落实为定义、执行留待 Phase 2」。汇总口径与明细不一致，容易高估收敛程度。

因此最终判定为：**原审查文件可作为有效复审输入，但应按本报告的 P1/P2 修订项更正；修订完成前，不应把它解释为 Protocol v0.1 已通过。**

## 3. 对原审查发现的采纳意见

### P1-1：阶段编号冲突——采纳，必须在 Phase 1 出口前解决

Protocol §14 使用 Phase 0–6，其中 Phase 0 是决策记录、Phase 3 是单项目垂直切片；当前计划 §4 使用 Phase 0–7，其中 Phase 0 是文档收敛、Phase 3 是安装准备、Phase 4 才是垂直切片。原审查对冲突的判断准确，且这是当前两份 Active 文档之间的真实治理缺陷。

建议采用单一编号源：由当前 Active plan 负责实施阶段编号，Protocol §14 只保留协议生命周期说明，并明确「实施阶段以 Active plan 为准」。如果确实需要在 Protocol 中保留阶段，应增加一张一对一映射表，并禁止两个文档各自定义同名 Phase。不能只在对话中约定映射。

### P1-2：D09 与 §7.3 的状态语义冲突——采纳，按原建议修正

Protocol D 表写的是「长任务承重事实确认后尽早持久化」，而 §7.3 规定只有写入并验证成功后，事实才能提升为已确认。D 表是高概率被单独查阅的规范摘要，当前措辞会重新引入「先确认、后持久化」的错误语义。

建议改为：

> 长任务承重事实应尽早持久化；写入并验证成功后方可提升为已确认。

修订后还应检查 D 表、正文、fixture 期望状态和失败语义是否使用同一顺序。

### P1-3：`operation_key` 无确定性推导规则——采纳，且不能只保留为候选方案

当前协议只提供 `reconcile-<stable-operation-key>` 占位符，却要求 §9.2 在重试时匹配相同 `operation_key`。由于 `run_id` 每次运行都会变化，崩溃恢复或新会话无法依靠当前文本重建该键，幂等分支因而不可实施。原审查的技术判断成立。

Phase 1 应形成可执行的正式规则，至少写清：规范化输入字段、字段顺序、排序与去重、编码和哈希方式、作用域、重复键的冲突处理，以及明确排除 `run_id`、时间戳等运行实例字段。原审查提出的「作用域 + 目标路径 + 排序后的拟变更 `claim_id` 集合 + 可选任务标识」可作为候选输入，但不能在协议中继续以未决占位符充当实现契约。还应规定同一键对应不同载荷或不同基线时必须停止并报告冲突，而不是静默复用。

### P2-1：`claim_id` 规范不足——采纳

原审查指出 `claim_id` 只有稳定性和不可复用性的原则，没有生成、作用域、碰撞检查和格式约束；该判断成立。它与 `event_id` 一样属于并发和审计的承重标识，应在同一轮标识符决策中明确。具体采用随机标识、内容寻址或其他方案可以由 Phase 1 决定，但协议必须固定一种可验证规则。

### P2-2：D01–D12 与来源草案之间缺少变更映射——采纳并补充边界

D 表相对响应文档的 D01–D12 有实际文字变化，尤其 D11 从操作者开放项变成了「本稿暂以中文作为工作规范源」。在没有操作者明确决策记录的情况下，这只能称为工作假设，不能称为已完成决策。

建议为每个 D 编号保留「来源表述、当前表述、变更类型、决策状态、责任人/决策者」字段；D11 应恢复为开放决定，或单独记录操作者已选择中文作为规范源。协议的中文稿可以作为当前工作载体，但载体语言与规范语言的最终决策不能靠文档创建者自行推定。

### P2-3：官方资料缺访问日期和章节定位——采纳

原审查正确指出协议只列 URL，没有把访问日期和章节/标题定位带入当前协议。建议补齐「来源、具体章节或标题、访问日期、用途/仅作参考模式」四项，以便后续区分官方事实、设计借鉴和本项目自身决策。

### P2-4：未跟踪历史文件的改写证据不足——采纳问题，修正处置建议

没有 Git 基线时，行数变化和抽查不能证明历史文件只增加了状态横幅。原审查识别的问题成立，但「先取得发布授权完成首次 commit」不是本任务的必要前提，也不能由审查文件自行暗示授权。

更合适的处置是：在每次历史文件降级轮次记录改写前后的 SHA-256、文件清单和允许的变更范围；如未来获得单独 Git 发布授权，再用 Git diff 补充验证。当前不应为了制造基线而擅自 stage、commit 或 push。

### P2-5：README 索引缺少新增文件维护规则——采纳，已列为本轮维护动作

原审查已经准确识别出「新增证据文件会使完整性声明失效」的问题，而且原审查文件自身就是该问题的实例。新增本复审结果后，索引还必须同时登记原审查文件和本结果文件。

README 应明确：凡新增审查、复审、证据或计划文件，产出该文件的同一轮必须更新索引；如果暂不更新，则完整性声明必须带明确的截止日期和未收录清单。本轮已把两个审查文件登记到 README，并完成链接复核。

### P3 项：采纳为伴随修订项

以下问题不阻塞当前进入定向复审，但应在下一轮文本修订中一并清理：

- 「推荐」不属于 Protocol §0.2 已定义的规范词汇，应改为已定义词或补充定义；
- README 的「中文译文」应改成「译文（任意语言）」等不依赖当前规范语言的表述；
- history 文件名时间戳与 `event_id` 时间戳格式应统一；
- 符号链接越界规则应增加对应 fixture 场景，或明确说明该规则的验证方式。

## 4. 新增报告层问题

### R-01（P2）：F-01–F-08 的汇总与明细不一致

原审查第 1 节的「六项已落实、两项显式推迟」不能从第 3 节表格推出。明细实际显示：F-01、F-06 可视为已落实；F-07 仅落实为 fixture 定义、执行尚未完成；F-02、F-03、F-04、F-05、F-08 各有部分落实、残留问题或后续决策。无论采用「文字落实」还是「执行闭环」口径，都不应使用「六项已落实」这一无条件汇总。

建议删除该计数，改为「八项均已逐项复核；其中若干项部分落实或留有明确残项，执行验证和正式决策仍按计划推进」，并以第 3 节明细表作为唯一状态来源。

### R-02（P2）：README 完整性结论是时间点快照，不是当前事实

原审查第 2 节把 README 的 16 个链接和 17 个文件当成当前完整性证据，但原审查文件写入后已经成为第 18 个文件且没有索引。原审查第 4 节对这一风险的文字说明是正确的，只是第 2 节的核验表和总评没有把它标成「截至审查时」的快照；本轮已通过 README 更新修复当前索引缺口。

建议在审查表中加入核验时间和目录快照，明确「审查文件写入后需重新核对索引」。本轮新增结果文件已执行同样的索引维护，未复制该缺陷。

## 5. 修订优先级与最终处置

建议按以下顺序处理：

1. 统一 Protocol 与 Active plan 的阶段编号及权威来源（P1-1）；
2. 修正 D09，并检查摘要层与正文的状态转移顺序（P1-2）；
3. 在正式决策记录中确定 `operation_key` 和 `claim_id` 规则（P1-3、P2-1）；
4. 为 D01–D12 增加来源到当前文本的变更映射，解决 D11 的决策权限问题（P2-2）；
5. 补官方资料定位、历史文件哈希证据、规范词汇和 fixture 缺口（P2-3、P2-4、P3）；
6. 修正原审查的 F-01–F-08 汇总，并维护 README 索引（R-01、R-02）。

最终处置：**原审查文件的核心结论予以采纳，状态为「可保留，需修订」；允许继续开展 Phase 1 定向复审和正式决策记录，但在上述 P1 项解决并完成对应验证前，不得宣布 Protocol v0.1 已批准、已安装或已完成实现。**
