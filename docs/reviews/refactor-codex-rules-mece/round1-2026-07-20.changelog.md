## Completeness finding after result review

The user recalled an existing rule requiring every new branch to describe the
problem, solution, acceptance, closeout, publication and final branch closure.
Read-only comparison confirmed:

- Saberu still carries most of that behavior in its required branch contract;
- the workspace candidate only retained branch/base/worktree announcement and
  generic plan/closeout concepts;
- no workspace rule required the complete create-to-retire branch task
  contract.

Root cause: the audit classified files and rule domains, not every normative
statement. The branch contract was therefore misclassified as project topology
because of the file that stored it.

Consequences:

- the prior content-ready claim is withdrawn;
- the displayed add/commit/push/PR command bundle is invalid and must not be
  executed;
- current rule implementation files remain frozen as an uncommitted candidate;
- the plan now requires a statement-level migration ledger, zero-unmapped gate,
  and explicit branch create-to-retire scenarios before implementation resumes.

The user then asked whether existing rule content itself had been evaluated for
efficiency and accuracy. The answer was only partially: prior work considered
duplication, ownership, resident-context size and publication friction, but did
not systematically evaluate every statement's necessity, correctness, trigger,
form, actionability, testability, freshness, recovery path and load cost.

The revised Phase 0 now requires a content-quality verdict before ownership
mapping. It distinguishes behavior-preserving rewrites from semantic changes,
which must be isolated for separate review. The frozen candidate therefore
cannot be treated as an acceptable target merely because its files are more
modular.
